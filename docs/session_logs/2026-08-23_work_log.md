## 1. 작업 흐름

### 1-1. 채팅 패널 3종 수리 (v1.12.0)

**배경/요구**: 사용자 지적 — "대화가 길어지면 스크롤이 생기는데 자동스크롤됐으면 좋겠고, 클로드가 던지면 코덱스 답변이 오기 전까지 클로드 발화가 올라오지 않음, 졸라 답답함". 이후 "턴 단위로 접을 수 있었으면" 추가.

**처리**: 세 증상의 원인이 서로 달랐다.

| 증상 | 원인 | 고친 곳 |
|---|---|---|
| 답변 전까지 발화 안 보임 | `send.sh` 가 답을 받은 뒤에야 턴을 **한 덩어리로** 기록 | `send.sh` 마커에 질문 원문·stamp·slug·subject 추가 → `chatDiscovery.ts` 가 pending 턴 생성 |
| 첫 턴은 카드조차 없음 | 문서가 생기기 전엔 파싱 대상이 없음 | 문서 없는 마커도 카드로 세움(`docUri` 빈 값, 링크만 생략) |
| 자동 스크롤 없음 | `render()` 가 스크롤을 안 건드림 | 바닥이면 따라가고 아니면 위치 보존 + `새 답변 ↓` |
| 턴 접기 없음 | — | 턴 헤더 클릭 접기, 접힌 줄에 질문 첫 줄 |

**결과**: 사용자 육안 확인 완료("버튼떴고, 턴 잘접혀", "클로드가 던진거 먼저 나오고 코덱스 답변기다리고 … 정상인듯해").

**설계 판단 하나**: 대기 상태를 **문서가 아니라 마커**로 푼 것. 문서에 질문을 미리 쓰면 실패 시 반쪽 턴이 기록에 남고, in-flight 복구·턴 카운트와 얽힌다. 문서는 확정된 것만 담는다는 원칙을 지켰다.

### 1-2. IVR 서버 "2차부터 기록이 안 쌓인다" 사고

**배경/요구**: 사용자 — "IVR서버에서 스킬호출후 1번 채팅기록은 보이는데 두번째부터는 채팅기록 쌓이지 않음, 심각한 문제임". "이건 스킬버그지?"

**처리**: 추측하지 않고 서버를 직접 봤다. `find / -type d -name codex_rescue -path "*docs*"` 로 세 곳이 나왔고, 같은 슬러그 문서가 셋으로 갈라져 있었다.

| 시각 | 실행 위치 | 문서 | thread_id | 턴 |
|---|---|---|---|---|
| 21:05 | `/home/yeogi_callcrew` | `260822_210503_…` | `…6182e3` | 2 |
| 21:09 | **`/tmp`** | `260822_210958_…` | `…f750c4` | 3 |
| 21:13 | `/home/yeogi_callcrew/gateway` | `260822_211347_…` | `…4dfb30` | 2 |

**결과**: "기록이 안 남은" 게 아니라 **호출 위치마다 새 대화가 만들어진** 것. `send.sh` 가 `$PWD/docs/codex_rescue` 에 쓰고 이어받을 문서도 그 디렉토리에서만 찾기 때문이다. → `git rev-parse --show-toplevel` 기준으로 바꾸고 그 루트로 `cd` 까지 하도록 수정. 하위 폴더(`src/`)에서 호출해 루트 문서에 10턴째로 이어붙는 것을 실측 확인.

⚠️ 이 사고의 2차 피해를 사용자에게 선제 고지했다 — **2·3차 답변은 1차 맥락을 모르고 나온 답**이므로, 그걸 근거로 고친 코드가 있다면 되짚어야 한다.

### 1-3. 호출 경계 재설계 (CONSULT)

**배경/요구**: 위 수정 후 사용자가 조건을 명확히 했다 — "대화를 나누는 단위는 codex_rescue 호출단위로 해야데".

**처리**: 이 요구에는 셸이 풀 수 없는 지점이 있었다. `send.sh` 는 매 턴 새 프로세스라 "지금이 새 호출인가"를 알 수 없다. 내 가설(`--stamp` 를 호출자가 넘긴다)을 걸고 CONSULT 로 반박을 받았다.

**결과**: 가설 **부분 기각**. Codex 진단 — 문제는 상태 저장 수단의 부족이 아니라 **관측 가능한 경계 신호의 부재**다. 같은 호출의 2번째 턴과 새 호출의 첫 턴은 인자·환경·cwd·문서·시간까지 같게 만들 수 있어 구별이 불가능하고, PPID·환경변수·TTY·lease·daemon 중 스킬 호출과 수명이 일치한다는 계약을 가진 것이 없다.

채택한 대안: **`--start` / `--resume-stamp` 를 필수·상호배타**로. 강제력은 스탬프라는 문자열이 아니라 *필수 인자 + 검증 + 거부*에서 나온다(EDIT 게이트를 환경변수로 바꾼 것과 같은 구조).

Codex 가 **내가 놓친 결함**도 찾았다: 호출별 문서로 바꾸면서 in-flight 복구가 계속 "최신 슬러그 문서"를 닫으면, 새 호출의 첫 턴이 문서 생성 전에 죽었을 때 **무관한 과거 대화를 닫는다.** 마침 같은 날 마커에 `stamp`·`slug` 를 넣어 둔 것이 여기서 권위로 쓰였다.

### 1-4. CHAT 무한 대기 (탐색 차단 + 상한)

**배경/요구**: 위 CONSULT 를 던지기 전, 같은 질문을 CHAT 으로 먼저 시도했다가 **16분** 동안 돌았다. 사용자가 "지금 Codex가 죽은 것 같아" → 이어서 "개선이 필요함".

**처리**: 원인은 두 겹이었다. ①설계 질문을 핑퐁에 밀어 넣음(스킬 문서에 이미 금지된 것) ②"파일은 읽지 마라"를 빼서 탐색이 시작됨. 사용자 결정으로 **탐색 기본 차단 + `--explore` 해제**, **120초 상한**.

**결과**: 상한 구현이 관건이었다. 과거 `CR_TIMEOUT` 이 Windows 미작동으로 제거된 이력이 있어 `timeout` 명령을 피하고 **백그라운드 + 1초 폴링 + TERM→2초→KILL** 로 짰다. 상한 5초로 낮춰 실측: exit 124, **codex 프로세스 0개**(Windows 에서 실제로 죽는다), 문서 미기록, 안내 출력. 정상 질문은 8초로 통과.

| **`--new` 제거 → `--close-stamp`** | 닫을 대상을 glob 으로 추측해 잘못 고른 문서를 영구히 닫을 수 있었다 | `--new` 유지 | 기존 기능 제거 — 사용자 컨펌 후 진행 |
| **구형 호출을 오류로** | 새 계약을 우회할 길을 남기지 않는다 | 경고만 내고 기존 동작 | 다른 프로젝트에서 열려 있던 대화는 대화키로 다시 잡아야 함 |
| 탐색 **기본 차단** + `--explore` | 붙일지 말지 고민하다 빠뜨리는 것이 16분의 원인이었다 | 항상 차단 / 상한만 두기 | 코드를 봐야 하는 CHAT 질문은 한 단계 더 필요(그런 질문은 CONSULT 감) |

## 3. 시행착오

- **잘못된 가정**: 설계 비교 질문을 CHAT 으로 던져도 되겠지.
  **발견 경위**: 3분 타임아웃 → 백그라운드 → 16분 경과. 사용자: *"채팅인데, 이렇게 딥하게 하면 곤란하지 않아?"*
  **복구**: CONSULT 로 전환해 요청서에 가설·실패 이력을 담아 다시 던짐. 훨씬 나은 답을 받음.
  **교훈**: 스킬 문서에 이미 있던 규칙("무거운 질문은 CHAT 이 아니라 CONSULT")을 내가 어겼다. 규칙이 있는데도 어겼다는 것이 요점이다.

- **잘못된 가정**: 웹뷰 개행 검증에서 "평가된 HTML 에 **실제 개행 문자**가 있어야 한다".
  **발견 경위**: 자체 검증 스크립트가 FAIL 을 냄.
  **복구**: 기준이 반대였다 — 웹뷰가 받는 것은 **JS 소스 텍스트**이므로 문자열 리터럴 안에는 `\n` **두 글자**가 있어야 하고, 브라우저가 파싱할 때 개행이 된다. 기준을 바로잡고 실제로 `firstLine()` 을 파싱·실행해 동작까지 확인했다.
  **교훈**: 검증 스크립트의 기대값 자체를 의심할 것. FAIL 을 보고 코드를 고쳤으면 멀쩡한 코드를 망칠 뻔했다.

- **잘못된 가정**: TaskStop 으로 죽인 CHAT 은 아무것도 안 남겼을 것.
  **발견 경위**: CONSULT 의 변경 감지가 `260822_215221_chat_chat-session-boundary.md` 를 잡아 "Codex 가 응답 파일 외 변경"으로 보고.
  **복구**: 시각(22:11:16 — CONSULT 시작 22:01:55 이후)과 Codex 이벤트(해당 파일 관련 명령 없음)를 대조해 **내 CHAT 실행의 산물**임을 확인. Codex 무단 변경이 아니었고 되돌리지 않았다.
  **교훈**: 변경 감지는 "다른 프로세스의 변경"도 잡는다. 스킬 문서 경고대로 **Codex 가 했다고 단정하지 말 것**. 그리고 죽였다고 본 실행이 이미 끝나 있을 수 있다.

## 4. 발견한 코드베이스 함정

- 🔴 **`send.sh` 의 CHAT resume 호출은 `-C` 없이 cwd 에 의존한다.** (`# cwd 는 이미 CH_ROOT 이므로 -C 없이도 맞다` 주석) 문서 경로 기준만 프로젝트 루트로 바꾸고 **`cd` 를 하지 않으면** Codex 가 호출 위치의 트리를 본다. 첫 턴은 `-C "$CH_ROOT_W"` 를 명시하므로 **resume 턴에서만** 어긋나 발견이 늦어질 수 있다.

- 🔴 **Windows Git Bash 에서 `git rev-parse --show-toplevel` 은 `F:/…` 를, `$PWD` 는 `/f/…` 를 준다.** 형식을 섞으면 상대경로 출력(`${CH_DOC#"$CH_ROOT"/}`)과 `winp` 변환이 어긋난다. 해법은 **실제로 `cd` 한 뒤 `$PWD` 로 정규화**하는 것.

- 🔴 **웹뷰 템플릿의 개행은 소스에 `\\n` 으로 쓴다.** tsc 는 템플릿 리터럴을 문자열로만 보므로, 생성된 `out/*.js` 를 grep 하면 `'\\n'` 으로 보이는 것이 **정상**이다. 평가된 HTML 에는 `\n` 두 글자로 들어가고, 웹뷰가 그 소스를 파싱할 때 비로소 개행이 된다. 소스에 `\n` 을 쓰면 HTML 에 진짜 개행이 박혀 문자열 리터럴이 끊기고 SyntaxError 가 난다.

- **`timeout` 명령 없이도 Windows 에서 상한을 걸 수 있다.** 백그라운드 실행 + `kill -0` 1초 폴링 + TERM → 2초 → KILL 로 codex.exe 가 실제로 사라지는 것을 실측했다. 과거 `CR_TIMEOUT` 제거 사유(`timeout` 미작동)는 구현 방식의 문제였지 원리의 문제가 아니었다.

- **in-flight 마커의 귀속 키는 `(stamp, slug)` 다.** 마커 경로는 slug 기반(`.chat_<slug>.inflight`)이므로 **락도 slug 단위로 유지**해야 한다. 락만 stamp 별로 쪼개면 같은 마커를 두 실행이 덮어쓴다(Codex 지적).
