## 1. 작업 흐름

### 1-1. Codex 패널 — 잘린 줄을 눌러 펼치기 (v1.9.3)

**배경/요구**: 활동 목록의 "말"(agent_message) 행이 `text-overflow:ellipsis` 로 잘려 읽을 수 없었다.
사용자 요구가 대화 중 세 번 바뀌었다 — ①워드랩으로 개행 → ②"아니면 클릭하면 펼쳐지게" → ③"전문보기 처럼"
→ ④"맨뒤에 ... 있는건 무조건 누르면 펼쳐지게" → ⑤"아코디언 형식이지?"

**처리**:
- `renderItem` 을 `<details class="row">` + `<summary class="it-head">` 구조로 재작성 ([codexRescuePanel.ts](../../src/codexRescuePanel.ts))
- 잘림 판정은 **레이아웃 후 실측** — `markClipped()` 가 `scrollWidth > clientWidth + 1` 로 판정하고,
  리사이즈·폰트 변경·행 닫힘 때 재측정한다. 열린 행은 라벨이 워드랩/숨김 상태라 측정에서 제외
- 펼칠 게 없는 행은 `.plain` 을 붙여 클릭을 `preventDefault` 로 삼킨다
- 아코디언은 `details.row` 만 대상. **명령 그룹(`details.cmdgroup`)은 제외** — 글이 아니라 행을 담는 상자다
- 기존 "전문 보기" 별도 줄과 `cx.readMore` i18n 키 제거

**결과**: 컴파일·웹뷰 검사 통과, 사용자 확인 완료, 마켓 1.9.3 게시 실측

## 3. 시행착오

### 3-1. 웹뷰 주석에 백틱을 써서 두 번 터뜨림

- **잘못된 가정**: "백틱 금지"가 코드 문자열에만 해당한다고 여겼다
- **발견 경위**: `` // `body` is the full message text `` → `TS1005: ';' expected`.
  고친 뒤 CSS 주석의 `` /* `.plain` marks rows */ `` → `TS2339: Property 'plain' does not exist on type 'string'`
- **복구**: 작은따옴표로 교체
- **교훈 한 줄**: `getHtml` 의 템플릿 리터럴 안에서는 **주석도 문자열의 일부다.** 백틱은 어디에도 못 쓴다

### 3-2. 복구를 눌렀는데 아무 일도 안 일어나는 것처럼 보임

- **잘못된 가정**: 파일이 제자리로 돌아가면 사용자가 복구 성공을 인지할 것이다
- **발견 경위**: 사용자가 *"문서만있는거 복구하니까, 복구 안돼는디?"* → 디스크 실측 결과 **복구는 정상**이었고
  `.trash/` 는 비었고 문서는 원위치에 있었다. 문제는 패널이 `.log/*_events.jsonl` 로만 카드를 그린다는 것 —
  로그를 완전 삭제한 실행은 카드가 될 재료가 없다
- **복구**: `discoverRuns` 가 문서도 스캔해 events 없는 stamp 를 `docsOnly` 카드로 만든다.
  early return 조건도 완화(`.log/` 가 없어도 문서가 있으면 진행)
- **교훈 한 줄**: **"파일이 맞게 놓였다"와 "사용자가 됐다고 인지한다"는 다른 문제다.** 후자를 확인하지 않으면 정상 동작이 버그로 신고된다

### 3-3. 사용자 요구를 절반만 반영

- **잘못된 가정**: *"휴지통에 넣는거니까 물어 볼필요 없이 다삭제하고, 휴지통에서 제거 할때만 물어 보면"* 에서
  앞부분(질문 제거)만 구현하고 뒷부분(완전 삭제 시 질문)을 단순 확인창으로 처리했다
- **발견 경위**: 사용자 *"완전 삭제할 때 원본까지 삭제할 건가 물어봐야 될 거 아니야?"*
- **복구**: 질문을 **옮긴** 것으로 재구현. 덤으로 드러난 것 — 문서만 남았을 때 확인 버튼 라벨이
  `기록 + 문서 삭제` 로 남아 있어 "같은 질문을 두 번 받는" 느낌의 원인이었다
- **교훈 한 줄**: "A 말고 B" 지시는 **A 제거 + B 추가**가 한 쌍이다. 절반만 하면 요구가 사라진 것처럼 보인다

### 3-4. vault 레포 divergence 로 스킬 배포 2회 실패

- **발견 경위**: `skill_cp_install deploy` → `! [rejected] main -> main (fetch first)` →
  `git pull --ff-only` 도 `Not possible to fast-forward`
- **원인**: 다른 머신의 Obsidian 앱이 노트 커밋을 올려둔 상태. 내 커밋 1개와 갈라짐
- **복구**: 건드린 파일이 전혀 겹치지 않음을 확인(`git diff --name-only origin/main...HEAD`)한 뒤
  사용자 컨펌을 받고 `git pull --rebase` → `git push` → `deploy` 재실행
- **교훈 한 줄**: `deploy` 는 **push 안 된 커밋이 있으면 중단**하는 안전장치가 있다. rebase 후 수동 push 가 필요하다

### 3-5. 테스트 재료가 없어 검증이 막힘

- **발견 경위**: 사용자가 로그를 전부 완전 삭제한 뒤 *"재료가 없어서 태스트를 못하겠네"*
- **복구**: 다른 프로젝트(crewPhone)의 실제 실행 기록을 복사해 stamp·slug·subject 만 바꿔 3건 생성.
  구성을 달리해(기록+문서 / 기록+문서 / 기록만) 모든 경로를 덮게 했다
- **함정**: `python -c` 에 MSYS 절대경로(`/f/workspace/...`)를 넘겨 `FileNotFoundError`.
  Windows 네이티브 python 은 그 형식을 모른다 → status.json 은 셸 `printf` 로 생성
- **교훈 한 줄**: 파괴적 기능의 검증에는 **버려도 되는 재료를 먼저 만들어 두는 편**이 빠르다

## 4. 발견한 코드베이스 함정

### 4-1. 웹뷰 파일의 백틱 — 주석 포함 (전문)

`codexRescuePanel.ts` 의 `getHtml()` 과 `workflowPanel.ts` 의 동일 함수는 **전체가 하나의 템플릿 리터럴**이다.
그 안의 HTML·CSS·JS·**주석**은 전부 문자열이다. 따라서:

- **백틱을 쓰면 그 지점에서 템플릿 리터럴이 끝난다.** 뒤따르는 내용이 JS 로 해석되며 엉뚱한 에러가 난다
  (`TS1005`, 혹은 `` `.plain` `` 처럼 프로퍼티 접근으로 보이면 `TS2339`)
- `${` 도 치환으로 먹힌다
- 개행은 `\\n` 으로 **이중 이스케이프** — 한 번만 쓰면 실제 개행이 되어 JS 문자열이 두 줄로 쪼개진다
- tsc 가 통과해도 런타임에 스크립트가 통째로 죽을 수 있다. **`node tools/check-webview.js out/codexRescuePanel.js out/workflowPanel.js` 를 반드시 돌린다**
- 증상: 패널이 영어로 보이고 카드가 하나도 없다

### 4-2. `discoverRuns` 는 `.log/*_events.jsonl` 이 목록의 기준이다

카드 한 장의 존재 근거는 이벤트 로그다. 문서(`_request_`·`_response_`·`_review_`)는 **부속물**로만 취급됐다.
그래서 로그를 지우면 문서가 멀쩡해도 실행이 목록에서 사라졌다.

1.10.1 에서 문서 스캔을 합집합에 넣었지만, **`docsOnly` 실행은 정보가 근본적으로 부족하다**:

- `mode`·`scope`·`subject`·토큰 수·활동 내역 전부 status 사이드카와 이벤트 로그에 있었다 → 복원 불가
- `startedAtMs` 는 stamp 에서 역산, `endedAtMs` 는 응답 문서의 mtime 이 최선
- 그래서 모드 칩을 그리지 않는다. **없는 값을 그럴듯하게 채우면 거짓 정보가 된다**

### 4-3. 같은 stamp 재실행 — 복구가 덮어쓰면 안 되는 이유

`codex_rescue` 는 죽은 요청을 **같은 stamp 로 재실행**한다(RESUME 모드).
따라서 휴지통에 있던 `260821_042513_response_foo.md` 가 원위치로 돌아가려 할 때,
그 경로에 **재실행이 만든 새 응답**이 이미 있을 수 있다.

`restoreTrashed` 는 `statOf(dst)` 로 먼저 확인하고, 존재하면 `conflicts` 에 넣고 건너뛴다.
그리고 **충돌이 하나라도 있으면 bin 을 지우지 않는다** — 지우면 남겨둔 파일까지 사라진다.

### 4-4. `purgeTrashed(includeDocs=false)` 는 meta.json 을 다시 쓴다

로그만 지우면 `entries` 에 없는 파일이 남는다. 그대로 두면 나중 복구가 존재하지 않는 파일을 찾는다.
그래서 survivors 로 manifest 를 재작성하고, survivors 가 0이면 bin 을 통째로 지운다
(빈 행이 남아 복구를 눌러도 아무것도 안 돌아오는 상황 방지).

**부작용**: 재작성된 meta 에는 `trashRun` 이 넣은 `mode` 가 그대로 남는데,
그 값이 `docsOnly` 카드에서 온 것이면 부정확하다. 지금은 빈 값으로 넘겨 `"mode"` 자체가 빠진다.
