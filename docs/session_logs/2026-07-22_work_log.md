### 1-2. Phase 0 분리 계획 (워크플로우 13에이전트)
- extension.ts를 10영역으로 나눠 병렬 분석 + 종합 + 적대검증 2 = 13에이전트.
- **첫 실행 전멸**: JSON 스키마 키를 한글로 지어 API 400(키는 `^[a-zA-Z0-9_.-]$`만). 키 영문화 재실행 성공(63만 토큰, 16분).
- 적대검증 2개 모두 `risky` → 코딩 전 mustFix 11개 도출.

### 1-3. 안전 분리 13모듈 (무중단 진행)
- **방식**: 순수 함수/상태는 그대로 옮기고 import로 대체(동작보존). 위험한 이관(planLang 순환 등)은 보류.
- **순서**: fs → logger(채널 주입) → tokenParser → format/displayName/textFormat → pathCodec/modelLimits/display → sound(runtime 주입) → beepGate(Map/Set export + isFirstScan getter/setter) → stageIndicator(planLang 콜백 주입 + StageInput 구조적 타입).
- 매 단계 `npm run compile` 통과. v1.7.44/45/46 실동작 검증(사용자 재로드 확인).

### 1-4. Codex 교차검증
- 사용자가 **복사용 프롬프트**로 Codex에 검증 요청 → [PHASE0_REFACTOR_CROSS_REVIEW.md](../PHASE0_REFACTOR_CROSS_REVIEW.md) 생성.
- **판정**: 13모듈 동작보존 승인 가능. 순수 함수 AST 대조로 본문 일치 확인. `stage dispose 재생성`만 수정 필요.

### 1-5. stage dispose 수정
- **원인**: 내가 `disposeStage()`에 추가한 `stageStatusItem = null` (원본 ce1933d엔 없음) → dispose 후 늦은 refresh가 `ensureStageItem()`으로 아이템 재생성 → 누수.
- **수정**: null 대입 2개 제거 → 원본 cleanup과 동일. (Codex는 `stageDisposed` 가드 플래그를 권했으나, "리팩터링이 추가한 차이만 되돌린다"는 Phase 0 원칙상 null 제거가 더 정확 = 근본 원인 제거.)

## 3. 시행착오
- **워크플로우 스키마 키 한글** → API 400 전멸. **한글은 값에만, 키는 영문.** (키 영문화로 복구)
- **stageIndicator 순수 이동 시도** → `planLang()`·`SessionInfo` 의존 발견. 콜백 주입(`isKorean`) + 구조적 타입(`StageInput`)으로 우회.
- **disposeStage에 null 대입 추가** → 재생성 누수. Codex가 잡음, 되돌림.

## 4. 발견한 코드베이스 함정
- extension.ts: `refreshPlanUsage ↔ refreshAllSessions` **양방향 순환**. 모듈 분리 시 콜백으로 단방향화(controller 서로 import 금지, extension이 wiring).
- **primer 검증 시간결합**: `await refreshPlanUsage()` 직후 **동일 continuation에서** `lastUsage.sessionResetAt` 동기 읽기. `void`화·EventEmitter·추가 `await`·반환 snapshot 사용 전부 금지(타이밍 깨짐).
- **disposeStage에서 StatusBarItem 참조를 null로** 만들면 `ensureStageItem`이 재생성 → 종료 후 유령 아이템 누수.
- **Codex rollout JSONL에 승인/입력 대기 이벤트 없음** (전수 grep 0건). app-server 실시간 notification으로만 나감 → 우리 확장은 대기 상태 감지 불가.
