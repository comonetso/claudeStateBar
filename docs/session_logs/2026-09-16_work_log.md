**처리**: `find ... -newermt`로 최근 수정 파일 확인 → SKILL.md(1414→1633줄)·send.sh·

상태였음을 확정.

### 1-2. 민감 정보 마스킹 판단
**배경/요구**: 글로벌 스킬 파일에는 서버 이름 4종(Calladmin·AI_IVR·DBServer·SportedAWS),
개인 호칭("리규형님"), 백업 경로, Windows 사용자 경로(`C:\Users\bluec\...`)가 실측 기록으로
섞여 있었다. 이걸 그대로 공개 레포에 올릴지 판단이 필요해 AskUserQuestion으로 확인받았다.
**처리**: `sed`로 서버 이름→"서버 A/B/C/D", 호칭→"형님"(옛 공개본과 같은 방식), 사용자 경로→
`<user>`로 치환. 첫 시도에서 sed 표현식 오류로 백슬래시 하나가 누락(`Users<user>`)된 것을
grep 재검사로 발견해 즉시 수정.
**결과**: 최종 grep 재검색에서 서버 이름·호칭·백업 경로·개인 계정 경로 잔여 0건 확인.

### 1-3. 코드(확장 본체) 영향 여부 확인
**배경/요구**: codex_rescue 스킬 변경이 확장의 `src/providers/codexRescue/*`,
`src/codexRescuePanel.ts`가 읽는 상태 파일 스키마(`status.json`의 `mode`·`kind`·`state` 필드,
`.log/events.jsonl`)에 영향을 주는지 확인이 필요했다.
**처리**: `runDiscovery.ts`의 `decidePhase()`·`isReview` 판정 로직과 `send.sh`의
`write_status()` 함수를 대조.
**결과**: 필드 스키마는 그대로이고(`write_status`의 출력 형식 불변), 새로 추가된 것은
`stop_reason`·`status: partial` 같은 **문서 프론트매터** 값이라 확장 코드는 변경 없이도
정상 동작함을 확인. 그래서 이번 세션은 문서·스킬 사본만 바꾸고 `src/` 변경이 없다.

## 3. 시행착오

- **잘못된 가정**: sed 치환 스크립트를 한 번에 여러 -e로 묶으면서 괄호 없는 캡처 표현식 하나가
  깨져 "unterminated `s' command" 오류가 났는데도, 나머지 치환은 정상 실행된 결과만 보고
  넘어갈 뻔했다.
- **발견 경위**: 치환 후 grep으로 잔여 민감 문구를 재검색하는 습관대로 확인하다가
  `Users<user>`(백슬래시 누락)를 발견.
- **복구**: 별도 sed로 백슬래시 재삽입 후 재검증, node --check로 문법 확인.
- **교훈 한 줄**: 여러 sed -e를 한 명령에 묶을 때는 각각 독립적으로 문법 검증하거나,
  치환 후 반드시 재grep으로 결과를 확인한다 — "명령이 0 종료했다"는 "의도대로 됐다"의 증거가
  아니다.
