## 1. 작업 흐름

### 1-1. 코덱스가 파일을 못 쓰던 원인 — 다른 세션 조사분 반영

**배경/요구**: 사용자가 다른 세션(claudeState 프로젝트)에서 규명한 내용을 넘겨주며
"확인하고 배포해야 할 것 같다".

처음에 나는 이것을 **"codex_rescue 스킬을 수정했다"**로 오해하고 수정본을 찾아 헤맸다.
글로벌·레포·claudeState 세 곳을 다 뒤졌지만 08-26 상태 그대로였고, 해시까지 동일했다.
사용자가 조사 내용을 붙여준 뒤에야 **스킬 수정이 아니라 원인 규명이었음**을 알았다.

**처리**: `SKILL.md` 의 "트러블슈팅 — 실측으로 확인된 것" 섹션에 항목 신설.
기존 항목(`helper_sid_resolve_failed`)과 같은 형식으로 맞췄다.

**결과**: 소유자(Owner)가 `BUILTIN\Administrators` 인 것이 원인이고 ACL 은 무관하다는 것,
진단은 `Get-Acl`, 복구는 `takeown` + `icacls`, **경로 공백·`.gitignore`·깊이·정션은 대조실험으로
원인이 아님이 확정**됐다는 것까지 담았다. 별개 잠재 원인인 `C:\tmp` 와 예방용 `config.toml`
설정도 참고로 붙였다.

### 1-2. `C:\tmp` 정리

**배경/요구**: 코덱스 공식 이슈(openai/codex#30712)의 잠재 원인. 실제로 존재했다.

**처리**: 내용은 1~2월 playwright 찌꺼기 14개 + 오래된 vsix 등 **71MB**, 최근 30일 내 사용 흔적
없음. **삭제 대신 `C:\tmp` → `C:\tmp_old` 로 이름만 바꿨다** — 되돌릴 수 없는 삭제를 피했다.

**결과**: 코덱스가 보는 경로에서는 사라졌고 내용은 보존됐다.

### 1-3. 🔴 확장 문서 감사 (Codex 리뷰 1차) — 지적 4건 + 자체 발견 1건

**배경/요구**: *"내가 왜이러냐면, 지난번에 졸라 허접한 문서를 배포해서 개쪽당했거든"*

**처리**: `codex_rescue` REVIEW 로 커밋 안 된 문서 3개를 감사. 지적을 하나씩 코드로 대조했다.

**결과 — 5곳 수정.** 그중 셋은 나갔으면 곤란했다.

1. 🔴 **README 영·한이 정반대로 안내하고 있었다** — *"못 읽으면 자동시작을 끈다"*.
   오늘 오전에 고친 동작과 정확히 반대다. **마켓에 나가면 거짓 문서**가 된다

   **바로 위 두 줄**이 "열림=고정 / 닫힘=이동"이라 자기 문단과 모순이었다.
   **리뷰가 못 잡았고 내가 대조하다 발견**했다
3. **10분 복구가 README 에 없었다** — 동작 변경인데 안내가 없어 사용자가 예상할 방법이 없었다
4. **절전을 "놓친 엣지"의 예로 든 것** — `wasOpen` 은 globalState 라 절전을 넘어 유지되고,
   깨어난 첫 관측에서 엣지가 정상 발생한다(`credentials.ts:220`)
5. `sixty-five` 에 단위 누락

**배경/요구**: 사용자가 "스킬의 리드미 업데이트 및 GitHub 배포도 영/한 잘 작성됐는지" 확인 요청.

- **오독**: CI 가 `success` 라 게시가 끝난 줄 알았다.
  **발견 경위**: 마켓 API 는 여전히 1.12.0. 워크플로우에 `continue-on-error` 주석이 있었다.
  **복구**: `gh run view --log` 로 `Published … v1.14.0.` 문자열을 직접 확인했다.
  **교훈**: `continue-on-error` 가 걸린 단계는 **실패해도 success 로 표시된다.**

## 4. 발견한 코드베이스 함정

### 4-1. 🔴 `continue-on-error` 는 CI 결과를 못 믿게 만든다

`.github/workflows/publish.yml` 의 게시 단계에 주석이 있다 —
*"Marketplace / Open VSX need secrets (VSCE_PAT / OVSX_PAT). continue-on-error so a ..."*

시크릿이 없거나 게시가 실패해도 **단계는 `success` 로 표시되고 전체도 success** 다.
배포 확인은 반드시 로그의 `Published <publisher>.<name> vX.Y.Z.` 문자열로 한다.

### 4-2. 게시 직후 마켓 API 는 옛 버전을 준다

`vsce` 로그가 명시한다 — *"Extension URL (might take a few minutes)"*.
`extensionquery` API 로 조회하면 게시 성공 후에도 한동안 이전 버전이 나온다.
**API 결과로 실패 판정하지 마라.**

### 4-3. 🔴 REVIEW 의 스코프 플래그와 집중 지시는 함께 못 쓴다 — 그 결과가 비싸다

`codex exec review` 는 `--uncommitted`/`--base`/`--commit` 과 `[PROMPT]` 가 배타적이다
(`SKILL.md` 에 이미 적혀 있다). 집중 지시를 주면 `send.sh` 가 스코프를 **문장으로 녹여** 넣는다.

여기까지는 알려진 것인데, **문장으로 녹은 "커밋 XXX 를 리뷰하라"를 Codex 가 따라가지 못한다.**
diff 를 못 찾고 저장소 전체 탐색으로 빠진다. 8분간 명령을 수십 개 태웠다.

→ **파일 경로를 직접 지목하고, 열지 말아야 할 것을 명시해라.**
`SKILL.md` 의 CHAT 실측이 이미 같은 결론을 냈다 — *"비용은 탐색 허용이 아니라 대상 미지목에서
나온다."* REVIEW 에도 똑같이 적용된다.

### 4-4. 🔴 한글 "검토요청"은 CONSULT 다 — `review` 로 번역하면 모드가 뒤바뀐다

`SKILL.md` 인자 표에서 `검토요청해`·`분석해줘` 는 **CONSULT**, `리뷰시켜` 는 **REVIEW** 다.
영문 README 에서 "분석·검토요청"을 `analysis and review requests` 로 옮기자
**한 문장 안에서 "review 는 켜져 있다"와 "Review 는 없다"가 공존**하게 됐다.

→ 영문 문서에서 모드를 가리킬 때는 `CONSULT`/`REVIEW` 같은 **모드 이름**을 쓰거나,
`the analysis mode` 처럼 하나만 가리키게 써라.

### 4-5. 중단된 codex 실행은 고아 프로세스와 락을 남긴다

`TaskStop` 은 bash 를 죽이지만 `codex.exe` 는 남는다(207MB 짜리가 계속 돌고 있었다).
그대로 두면 **한도를 계속 먹는다.** 락 파일(`.log/.<스탬프>.lock`)도 남아 같은 슬러그 재실행을 막는다.

→ 중단 후에는 `tasklist | grep codex` 로 확인하고 정리해라. 다른 슬러그로 재실행하면
락 충돌은 피할 수 있지만 프로세스는 별개 문제다.

## 5. 사용자 핵심 발언

- > "그리고 난다음 결과를 가지고 문서등을 다시 정제해서 배포하는걸로
  > 내가 왜이러냐면, 지난번에 졸라 허접한 문서를 배포해서 개쪽당했거든"
  — **이번 감사의 이유.** 리뷰를 배포 **전에** 돌리자는 내 제안이 받아들여진 근거이기도 하다.
  결과적으로 마켓에 나갈 뻔한 거짓 서술 3건을 걸렀다.

- > "스킬은 따로 해서 두번돌려야하지 않겠어?"
  — 저장소가 다르면 diff 도 다르다는 것을 사용자가 먼저 지적했다. 맞는 판단이었다.

- > "끊고 다시 돌리"
  — 8분 헤매던 리뷰를 중단시킨 결정. **매몰비용에 끌려가지 않는 판단**이었고,
  재실행은 훨씬 빨리 끝났다.

- > "빼먹지말고"
  — v1.12.0 이후 커밋 13개를 전수 대조하게 만든 지시. 그 대조에서
  `claudeState.telegramNotifyOnReset` 누락을 찾았다.
