## 1. 작업 흐름

### 1-1. 죽인 에이전트가 패널에서 영원히 "진행 중" (핵심 버그)
**배경**: 사용자가 워크플로우 모니터링 패널에서 태스크(에이전트)를 TaskStop으로 죽여도 계속 "N/M 진행 중"으로 도는 것으로 표시된다고 제보 (사진: 원격 서버의 grounding-success-audit).
**원인**: 두 스캔 경로 모두 "완료"만 감지, "죽음" 미감지.
- journal 기반(wf_*): `isDone = doneSummary.has(id)` — journal.jsonl은 started/result 2종만 기록, 죽이면 result 안 남음 → 영원히 running.
- Task 기반: 마지막 assistant가 end_turn/긴최종답변일 때만 done. 죽이면 미충족 → running.

### 1-2. 정확 신호 탐색 — 시간 휴리스틱 거부 → 실증 실험
**요구**: 사용자가 "시간으로 감지=대충. 다른 방법 찾아라" + "3마리 풀어서 1마리 죽여봐(Sonnet)".
**처리**: Sonnet 에이전트 3마리를 `ping -n 60`으로 띄우고 1마리 TaskStop → 디스크 관찰.
**발견**: 죽이면 `agent-<id>.jsonl` 끝에 `{"type":"user", ... "[Request interrupted by user for tool use]"}` 레코드가 붙는다. **명시적 kill 신호.** meta.json엔 상태 필드 없음(불변).
**교차검증**: 기존 죽은 wf 3개(wf_141cdab9/wf_47b1a24a/wf_4cb5e6b9)에서 "journal result 없는 미완 agent" ↔ "interrupt 마커 있는 agent" 1:1 정확 일치.

### 1-3. stopped 상태 구현 (A안: 별도 "중단됨")
`agentWasInterrupted(lines)` 헬퍼 + 양 경로 status 3분기(running/done/stopped). 회색 점 + "중단됨" 라벨 + "N 완료·M 중단" 배지. stopped는 running 아니므로 진행중 카운트 자동 제외.

### 1-4. 짧은 완료 답변이 running 고착 (재로드 검증 중 발견)
**발견 경위**: 재로드하니 중단됨(stopped)은 정확한데, 완료된 핑 에이전트("핑 완료")가 여전히 주황(running).
**원인**: Task 완료 판정이 `sr==='end_turn' || (1500자↑ && 4초settled)`. "핑 완료"는 sr=null + 짧음 → 그물 통과 못함.
**수정**: 크기(1500자) 조건 제거 → "텍스트만(tool_use 없음) + 4초 idle"이면 done. 근거: 중간 설명 텍스트는 ~0.6초 내 도구 엔트리가 따라오므로, settle된 텍스트-only 마지막 엔트리는 최종 답변.

### 1-5. stopped 시 제목 경과시간 안 멈춤 (재로드 검증 중 발견)
**원인**: 경과 멈춤 조건이 `every(status==='done')` → stopped 있으면 거짓 → 계속 카운트업.
**수정**: `every(status!=='running')` (running 0이면 done·stopped 무관하게 종료 → endedAt 고정).

## 4. 발견한 코드베이스 함정

- **journal.jsonl은 started/result만 기록** — 죽음/취소 레코드 없음. 죽음은 오직 agent-*.jsonl의 `[Request interrupted]` 마커로만 판정 가능.
- **워크플로우는 부모 세션 JSONL에 tool_use가 아니라 `isSidechain=true`로 기록** → 부모 tool_result 매칭으로 완료 감지 불가.
- **Task 완료 판정의 1500자 크기 게이트가 짧은 최종 답변을 놓침** → 완료 에이전트가 running 고착.
- `getShortModelName`처럼 새 상태 추가 시 3곳(감지·배지·경과멈춤) 모두 손봐야 일관 — allDone 조건이 여러 곳에 중복.
