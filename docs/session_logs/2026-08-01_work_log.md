## 1. 작업 흐름

### 1-1. 실측 스키마 조사 (구현 전)
**배경**: 설계 문서가 2026-07-22 기준이라 8일 경과. 스키마 드리프트 가능성을 먼저 확인.
**처리**: `~/.codex/sessions` 20개 rollout 전수 스캔 — 타입 분포, 필드 형태, 파일 크기, 줄 크기.
**결과**: 문서에 없던 사실 6건 발견(§4-1~4-6). 이 조사가 이후 설계를 전부 결정했다 — 특히 **14.1MB 파일 / 3.6MB 단일 줄**이 head/tail 윈도우 전략을, **44.9KB session_meta**가 윈도우 크기를 정했다.

### 1-2. Phase 1 구현
5개 신규 모듈 + 공용 타입 분리. `SessionInfo`를 [src/core/sessionTypes.ts](../../src/core/sessionTypes.ts)로 빼서 provider가 extension.ts를 import하는 순환을 피했다.
Codex 세션을 `SessionInfo`로 정규화하니 **렌더링·색상·idle·비프·숨김이 전부 재사용**됐다. 특히 `task_complete`를 `lastAssistantEndTurnAt`에 매핑해 기존 settle-debounce를 그대로 태운 게 핵심.

### 1-3. Remote-SSH — 잘못 결론 냈다가 뒤집음
**배경**: 초기 구현에서 Node `fs` byte-range read를 쓰고 "원격은 range read가 없으니 미지원"이라고 문서에 명시.
사용자: *"SSH로 접속해서 작업하는 게 안 뜨면 무슨 의미가 있어? 대부분은 원격 서버인데"*
**처리**: 재검토하니 근거가 코드 안에 있었다 — [src/core/fs.ts:7](../../src/core/fs.ts#L7)에서 **Claude는 이미 원격 파일을 통째로 읽고** 있고, 이 PC의 Claude 세션 최대치가 9.2MB. Codex 14.1MB와 같은 급. byte-range는 로컬 *최적화*였을 뿐 원격 불가 사유가 아니었다.
**결과**: URI 스킴으로 읽기 전략을 분기(로컬=byte-range, 원격=전체읽기+mtime캐시). 원격 홈 탐색은 Claude의 `getClaudeBaseUri()` 패턴을 그대로 복제.

### 1-4. 사용량 — 두 번 뒤집음
**1차**: rollout의 `rate_limits` 스냅샷을 읽음. 문서 §11.2의 2순위.
**사용자 지적①**: *"주간소진이 갱신이 안 되고 있어... 이건 치명타"* → 스냅샷은 Codex가 일할 때만 갱신되는데 한도는 7일 롤링이라 안 써도 값이 내려간다. 굳어버린다.
**2차**: app-server `account/rateLimits/read` 실시간 조회로 전환(문서 §11.2의 1순위). 실측 591~850ms.
**사용자 지적②**: *"코덱스 주간한도가 세션마다 틀려... 이러면 작업하는 의미가 없잖아"* → **내 설계 실수.** 세션별로 자기 rollout 스냅샷을 읽게 만들어서 한 계정이 52/30/28/22/19% 를 동시에 표시했다.
**3차**: 계정 단위로 통일(`accountCodexUsage()`). 폴백도 "전 세션 중 최신 스냅샷 1개"를 골라 전체에 동일 적용.

### 1-5. 리셋 시각 날짜 누락
스크린샷 제보: `오후 4:16 (수) (4일 13시간 후)` — 7일 주기인데 요일만으로는 이번 주인지 다음 주인지 모른다.
`resetAtLabel()`이 당일이 아니면 요일만 붙이던 것을 `8/5 (수) 오후 4:16`으로 변경. **Claude 주간 리셋도 같은 함수라 동시에 개선**됐다(5시간 세션은 당일이라 그대로).

## 3. 시행착오

- **잘못된 가정**: "byte-range read를 못 쓰면 Remote-SSH 불가"
  **발견 경위**: 사용자가 "대부분 원격 서버인데 의미가 있냐" 지적 → 재검토
  **복구**: `core/fs.ts`가 이미 원격 전체읽기를 하고 있었고 Claude 최대 파일이 9.2MB라 비용 선례가 이미 존재
  **교훈**: **"최적화를 못 쓴다"와 "기능이 불가능하다"는 다른 문장이다.** 기존 코드가 같은 문제를 어떻게 풀었는지 먼저 봤어야 했다.

- **잘못된 가정**: "rate_limits는 세션 데이터다"
  **발견 경위**: 사용자가 "세션마다 값이 틀리다" 지적. 내 검증 로그에 이미 30/28/22/19/2/48% 가 찍혀 있었는데 **다르다는 사실 자체를 이상하게 여기지 않았다.**
  **복구**: 계정 단위로 통일
  **교훈**: 검증 출력에 이미 답이 있었다. **"같아야 할 값이 다른데 그냥 지나친 것"** — 값의 의미(계정 vs 세션 스코프)를 먼저 정의했어야 했다.

- **잘못된 가정**: head 64KB면 `session_meta`(18KB 관측)를 커버한다
  **발견 경위**: 20개 중 1개만 모델명 blank → 그 파일만 `session_meta`가 44.9KB이고 `turn_context`가 165KB 지점
  **복구**: head 256KB + 못 찾으면 1MB 재시도
  **교훈**: **1개 파일 관측치를 상수로 굳히지 마라.** 전수 검증이 아니었으면 못 잡았다.

- **잘못된 조작**: `package.json`을 `JSON.stringify`로 재작성 → 337줄 재포맷 diff
  **복구**: `git checkout package.json` 후 Edit로 최소 수정
  **교훈**: 설정 파일은 포맷도 내용이다. 부분 수정만 하라.

## 4. 발견한 코드베이스 함정 (위키 스킵 세션 — 전문 수록)

### 4-1. Codex rollout 실측 스키마 (문서와 어긋난 부분)
설계 문서(2026-07-22) 대비 2026-08-01 실측 차이:
- `response_item.custom_tool_call` **외에** `function_call` / `function_call_output` 이 병존(드리프트가 아니라 둘 다 존재)
- `event_msg.agent_reasoning` — 문서에 없음
- top-level **`compacted`** 타입 — 문서에 없음. §4-4 참조
- `session_meta.payload.context_window`는 **숫자가 아니라 객체** `{window_id}`. 컨텍스트 한도는 `task_started.model_context_window` 또는 `token_count.info.model_context_window`에서 가져와야 한다
- `task_started.model_context_window` — 문서에 없던 유용한 필드. token_count가 아직 없는 세션도 분모를 얻는다
- 관측 모델: `gpt-5.5`, `gpt-5.6-sol`, `gpt-5.6-terra`, `codex-auto-review` / effort: `low|medium|high|xhigh`

### 4-2. `session_meta.source`는 문자열일 수도 객체일 수도 있다
```
"vscode"                              ← 일반
{"subagent":{"other":"guardian"}}     ← 서브에이전트
```
문자열로 가정하고 파싱하면 서브에이전트 세션에서 깨진다. 이 PC에 실제 1건 존재.
`originator`도 볼 것: `codex_vscode` / `codex_work_desktop` / **`Claude Code`**(codex_rescue로 Claude가 띄운 Codex 세션, 실제 2건).

### 4-3. 파일 크기 함정 — 전체 읽기 금지
- 최대 파일 **14.1MB / 1435줄**
- **단일 줄 최대 3.6MB** (`compacted` 레코드)
- `session_meta`는 첫 줄이지만 크기가 **18KB~44.9KB로 파일마다 다름**
- 마지막 `turn_context`가 **165KB 지점**인 케이스 존재(턴이 적고 파일이 큰 세션)
→ head 256KB(모델 못 찾으면 1MB) + tail 1MB(토큰 못 찾으면 5MB) 윈도우가 이 관측치에서 나왔다.

### 4-4. `compacted` 레코드에는 대화 원문 전체가 들어있다
`payload.replacement_history`에 이전 대화 전체(~15KB, 사용자 메시지 원문 포함). **타임스탬프만 취하고 본문은 건드리지 않는다.** 진단 로그에 절대 흘리면 안 된다.

### 4-5. ★ `rate_limits`는 계정 단위다 (이번 세션 최대 실수)
각 rollout에는 **그 세션이 마지막으로 돌던 시점**의 계정 한도가 박힌다. 세션별로 읽으면 한 계정이 동시에 여러 값을 보인다 — 실측 `52/30/28/22/19%`.
계정 한도는 계정당 하나다. 반드시 **하나를 골라 전 세션에 동일 적용**할 것.
필드명 주의: rollout은 snake_case(`used_percent`, `window_minutes`, `resets_at`), app-server는 camelCase(`usedPercent`, `windowDurationMins`, `resetsAt`). **`resets_at`/`resetsAt` 둘 다 epoch 초** — ms로 변환 필요.

### 4-6. `task_complete` 이후에도 레코드가 온다
최종 `task_complete` 뒤에 `thread_settings_applied`가 붙는 세션이 실재.
→ "마지막 활동이 마지막 턴종료보다 새로우면 작업 중"이라는 Claude식 휴리스틱을 Codex에 그대로 쓰면 **끝난 세션에 '작업 중' 카운터가 뜬다.** Codex는 `task_started` vs `task_complete/turn_aborted` **순서**로 판정해야 한다(`codexActive`).

### 4-7. Codex app-server JSON-RPC 호출 레시피
```
codex app-server            # stdio, newline-delimited JSON
→ {"id":0,"method":"initialize","params":{"clientInfo":{"name":"...","version":"..."}}}
← {"id":0,"result":{...}}
→ {"method":"initialized","params":{}}          # 이 notification 필요
→ {"id":1,"method":"account/rateLimits/read","params":{}}
← {"id":1,"result":{"rateLimits":{"primary":{"usedPercent":52,"windowDurationMins":10080,"resetsAt":1785914166},...,"planType":"plus"}}}
```
- 메서드 전체 목록은 `codex app-server generate-json-schema --out <dir>` 의 `ClientRequest.json`에서 추출
- `account/usage/read`는 퍼센트가 아니라 **토큰 통계**(lifetime/일별 버킷) — 한도 표시에는 못 쓴다
- Windows npm 설치본은 `.cmd` shim이라 **`shell:true` 필요**. `child.kill()`로 orphan 안 남는 것 실측 확인
- `codex app-server`에 `daemon`/`proxy` 서브커맨드가 생겼다(문서 작성 시점엔 없었음) — 상시 연결이 필요해지면 재검토 대상

### 4-8. 남겨둔 진단 로그 (숨김 이슈 미해결)
[src/extension.ts](../../src/extension.ts)에 3종:
- `[hide] hid via menu (provider) <uri>` — 숨김 등록됨
- `[hide] auto-unhide (codex) ...` — 활동 감지로 **의도적** 복귀
- `[hide] hidden key no longer matches any discovered session: <uri>` — **키 불일치 = 진짜 버그**
세 번째가 뜨면 매 refresh마다 sessionFile URI가 달라진다는 뜻. 해결 전까지 제거 금지.
참고: 백그라운드 파일 쓰기는 **없음**을 실측 확인(3개 파일 모두 마지막 레코드가 `task_complete`). 따라서 "파일이 계속 갱신돼 auto-unhide"는 원인이 아니다. 유력 후보는 **여러 확장 인스턴스**(이 세션에 1.8.0을 5회 재설치했다).

### 4-9. 검증 probe 재작성 방법 (삭제됨 — `out/`은 gitignore)
Extension Host 없이 검증한 방법. 다시 필요하면 이렇게 만든다:
1. **파서 검증**: `out/providers/codex/*.js`는 vscode 의존이 없어 순수 node로 직접 require 가능
2. **provider 통합 검증**: `Module._load`를 후킹해 `require('vscode')`에 stub을 주입. stub의 `workspace.fs`를 Node `fs`로 구현하면 실데이터로 `findCodexSessions()`를 그대로 실행 가능
3. **원격 경로 검증**: 같은 stub에서 URI `scheme`만 `vscode-remote`로 바꿔 실행 → 로컬 결과와 필드 단위 비교. 이번에 5세션×12필드 전부 일치 확인
4. **app-server 검증**: `child_process.spawn('codex',['app-server'],{shell:true})` + §4-7 시퀀스

## 5. 사용자 핵심 발언

- > "클로드하고 동일한 경험으로 하기로 했는데? 단지 코덱스꺼는 코덱스 아이콘, 클로드면 클로드 아이콘" — Codex를 축소판이 아니라 **대등한 provider**로 취급하라는 요구. 사용량 표시를 Claude와 대칭으로 만든 근거.
- > "현재는 클로드에서 코덱스로 요청하는것이 있어서 두개의 세션이 동시에 존재할가능성이 졸라많아" — codex_rescue 흐름. **동시 표시가 예외가 아니라 기본 시나리오**.
- > "SSH로 접속해서 작업하는게 안뜨면 무슨 의미가 있어? 대부분은 원격 서버인데" — 원격이 주 환경. 로컬 전용 기능은 반쪽.
- > "코덱스 주간한도가 세션마다 틀려... 이러면 작업하는 의미가 없쟎아" — 계정 스코프 오설계 지적.
