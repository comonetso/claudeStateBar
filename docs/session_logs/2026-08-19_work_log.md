## 1. 작업 흐름 (커밋으로 복원 불가한 맥락)

### 1-1. 발단 — "스킬부터 분석해봐"에서 시작

사용자가 `/codex_rescue` 스킬 분석을 먼저 요청했고, 그 다음에야 진짜 요구가 나왔다:
**"스킬을 발동하고 난 다음 코덱스가 어느 정도 진행하고 뭘 하는지 깜깜이라서, 이걸 워크플로우 패널처럼 보여줄 수 없나."**

스킬 분석이 선행된 것이 결과적으로 결정적이었다 — `send.sh`를 읽지 않았다면 원인을 못 찾았다.

### 1-2. 원인 규명 — 재료는 이미 흐르고 있었다

`send.sh`는 이미 `codex exec --json`으로 실행하고 있었다. 이벤트는 실시간으로 나오는데
**흘러가는 곳**이 문제였다.

```
RUN_DIR=$(mktemp -d "/tmp/codex-rescue-<스탬프>.XXXXXX")   # ① workspace 밖 ② 랜덤 접미사
"$@" "$PROMPT" > "$EVENTS"                                  # 실시간 축적되지만 아무도 못 봄
cp -f "$EVENTS" "$LOGD/..._events.jsonl"                    # 끝난 뒤에야 복사
cleanup() { rm -rf "$RUN_DIR"; }                            # ③ 그리고 삭제
```

**볼 수 있게 되는 순간이 곧 이미 끝난 순간**이었다. 실행 중에 `/tmp/codex-rescue-*`를 직접
`tail` 쳐서 이벤트가 실시간으로 쌓이는 것을 눈으로 확인해 가설을 확정했다.

### 1-3. Codex 2차 검토 — 스키마 확정 + 진짜 버그 발견

`codex exec --json` 이벤트 스키마 실물을 본 적이 없었다(`.log/` 저장은 08-17 개정에 들어갔고
그 이후 실행이 없었다). 스키마를 모르면 파서를 지어내게 되므로 Codex에 물었고,
Codex가 정확한 태그(`rust-v0.145.0/exec_events.rs`) 소스로 8종 이벤트 계약을 확정해 줬다.

부수적으로 **실제 버그 두 개**를 잡아냈다 — §3-2 참조.

### 1-4. 요구가 커진 지점 — "이런건 공유를 해서 사용해야지"

처음엔 "내가 쓰는 특수 케이스니 배포하면 안 된다"였다가, 중간에 **공유 방향으로 바뀌었다.**
그에 따라 감지 기준을 **워크스페이스 → 스킬 설치 여부**로 바꾸고(발견성),
스킬 소스를 레포에 넣고(vsix 제외), 가이드 2종을 만들었다.

## 3. 시행착오

### 3-1. `tee` 버퍼링 — 근거 없이 걱정했다

- **잘못된 가정**: "Rust는 stdout이 파이프면 블록 버퍼링이므로 `| tee`를 붙이면 실시간성이 죽는다"고 사용자에게 **선제 고지**까지 했다
- **발견 경위**: Codex가 소스로 반박 — Rust std의 stdout은 **`LineWriter`(줄 버퍼링)** 이고, Node 진입점은 native `codex.exe`를 `stdio: "inherit"`로 spawn해 따로 모으지도 않는다
- **복구**: 실측으로 확정 — `tee` 적용 후 6초에 5줄 축적
- **교훈**: C stdio의 관례를 Rust에 적용했다. **언어별 stdout 버퍼링 정책을 확인하지 않고 일반론으로 경고하지 마라.**

### 3-2. Codex가 잡은 진짜 버그 — heartbeat 수명 계약

- **잘못된 구현**: codex 종료 직후 heartbeat를 죽이고 `finalizing`으로 넘어갔다. 그 아래로 전체 파일 스캔 2회 + 해시 + 로그 복사가 남아 있었다
- **결과**: 후처리가 30초를 넘기면 **멀쩡히 도는 실행이 `stale`로 오판**된다
- **복구**: 순서 변경이 아니라 **heartbeat 수명 연장** — 계약을 "codex가 살아있다"에서 **"send.sh가 살아있다"**로 바꿨다. 최종 status 기록 직전까지 유지
- **곁가지**: "status는 live인데 heartbeat 없음" 조합이 판정 불가 구간이었다 → heartbeat를 status보다 **먼저** 생성해 그 조합 자체를 없앴다

### 3-3. `error` 아이템을 전부 빨간 실패로 칠했다

- **발견 경위**: 사용자가 패널 스크린샷을 보내며 **"상단에 오류가 표시되는데, 코덱스가 오류가 난건가?"**
- **실제**: CLI 안내였다 (`clamping SessionEnd hook timeout to 3s`, `Skill descriptions were shortened...`)
- **뼈아픈 점**: Codex 응답 본문에 *"경고·deprecated·비치명 오류가 completed item으로 들어올 수 있다"*고 적혀 있었는데 **읽고도 코드에 반영하지 않았다**
- **복구**: `ItemStatus`에 `warn` 추가, 라벨 `오류`→`알림`
- **교훈**: **받은 답변의 문장을 코드로 옮겼는지 대조하라.** 읽은 것과 반영한 것은 다르다

### 3-4. 요청 크기 — 사용자 지적으로 20분이 1분 25초가 됐다

- **잘못된 판단**: 첫 REVIEW를 커밋 안 된 변경 **전체**로 던졌다(신규 3파일 + 대규모 수정 + 문서)
- **사용자 지적**: *"왜 이렇게 많이 실행을 하고 있지, 커맨드를? 간단한 걸 시키지, 오래 걸리잖아"*
- **실측 대비**: 전체 리뷰 = 명령 36건 / 20분(중단) vs 판단 대상만 담은 요청서 = 명령 4건 / **1분 25초**
- **교훈**: 검증이 목적이면 **요청을 작게 잘라라.** 요청서에 코드를 다 담고 "조사하지 마라"를 명시하면 탐색이 사라진다

### 3-5. 테스트 경로 — Windows Node는 MSYS 경로를 못 읽는다

`/tmp/...`를 Node에 넘겨 `MODULE_NOT_FOUND`·빈 결과가 두 번 났다. 스크립트 로직 문제로 오인할 뻔했다.
→ **Node에 넘기는 경로는 `C:/Users/.../Temp/...` 형태로.** bash 쪽 파일 조작은 MSYS 경로 그대로 써도 된다.

## 4. 발견한 코드베이스 함정 (전문)

### 4-1. `codex exec --json` 이벤트 계약 (0.145.0 실측 + 소스 확정)

최상위 8종: `thread.started`(thread_id) · `turn.started` · `item.started` · `item.updated` ·
`item.completed` · `turn.completed`(usage) · `turn.failed`(error) · `error`(message)

`item.type` 9종과 주요 필드:

| item.type | 필드 |
|---|---|
| `agent_message` · `reasoning` | `text` — **completed에서만 나온다** (started에서 의도적으로 걸러짐) |
| `command_execution` | `command` · `aggregated_output` · `exit_code` · `status` |
| `file_change` | `changes[{path,kind}]` · `status` |
| `web_search` | `query` · `action` — **action은 `{"type":"other"}`처럼 내용이 비어 표시 재료로 못 쓴다** |
| `mcp_tool_call` · `collab_tool_call` · `todo_list` · `error` | 각각 |

🔴 **없는 것**: 타임스탬프(어느 이벤트에도 없다) · 실시간 토큰(usage는 `turn.completed`에만) ·
reasoning delta · 확정적 파일 read 이벤트 · **전체 진행률 근거**

🔴 **`error`는 terminal이 아니다.** 0.145.0 매퍼는 이를 내보낸 뒤에도 Running을 유지한다.
🔴 **중단(`TurnStatus::Interrupted`)에는 terminal JSON 이벤트가 아예 없다.** 그래서 생사는
프로세스 생존(heartbeat)으로만 알 수 있다.

산술 검증: `item.started` 45 vs `item.completed` 57, 차 12 = `agent_message` 11 + `error` 1.

### 4-2. `aggregated_output`이 파일의 86%다

실측: 3회 실행 events 합계 901KB 중 **명령출력/도구결과가 774KB(85.9%)**.
한 줄이 63KB인 경우도 있었다(105줄에 409KB). **파서에서 아예 버려야 한다** —
버린 결과 패널 보관량이 409KB → 21KB(5.2%)가 됐다.

### 4-3. `codex exec`도 rollout을 남긴다 — P2 항목 무효화

`~/.codex/sessions/2026/08/19/rollout-...-01a0186d-...jsonl`,
`session_id` == `thread.started.thread_id`, `originator: "codex_exec"`, `source: "exec"`.

→ **2026-08-03부터 이월된 "실행 중인 Codex 세션이 rollout·SQLite 어디에도 없었다"는 건을
`codex exec`의 특성으로 결론 내리면 안 된다.** 다른 원인이며 재조사 대상이다.
덤으로 **rollout에는 timestamp가 있어** exec JSONL의 결정적 약점을 join으로 보완할 수 있다.

### 4-4. lock은 권위 신호가 아니다

`.log/.{stamp}.lock`은 **Codex의 workspace-write 범위 안**에 있다. 피감시자가 지울 수 있는 것을
감사·생사 판정의 권위로 쓰면 안 된다. `.log/`의 status·heartbeat도 마찬가지로
**UI 편의용 비권위 telemetry**다.

### 4-5. `turn.completed` ≠ 실행 종료

Codex 턴 성공일 뿐이고, 그 뒤로 `send.sh`가 변경 검사·응답 회수·로그 보존을 더 한다.
이걸 완료로 쓰면 그 구간이 통째로 "완료"로 잘못 표시된다. → `finalizing` 상태를 따로 뒀다.

### 4-6. rollout 파서를 exec JSONL에 재사용할 수 없다

rollout은 `{timestamp, type, payload}`, exec JSONL은 `{type, ...}`. 스키마가 다르므로
`tailReader.readSession()`을 그대로 부르면 **조용히 빈 결과**가 나온다.
offset/carry 패턴만 가져오고 accumulator는 새로 만들어야 한다.
(추가로 carry는 문자열이 아니라 **Buffer**로 들어야 UTF-8 경계에서 깨지지 않는다)
