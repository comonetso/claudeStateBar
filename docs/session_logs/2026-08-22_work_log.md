## 1. 작업 흐름

### 1-1. Codex 호출 경로를 먼저 실측했다

"코덱스를 호출하는 게 여러 가지"라는 사용자 지적에서 시작했다. rollout 의 `originator` 로 실측(최근 40건):

| 경로 | 건수 | 기록 위치 | 진행 패널 |
|---|---|---|---|
| `codex_exec` | 27 | `.log/` + rollout | ✅ |
| `codex_vscode` | 10 | rollout only | ❌ (상태바만) |
| `Claude Code` (codex-plugin-cc) | 3 | rollout only, cwd=`%TEMP%\codex-plugin-cc` | ❌ |

그중 1건은 **Codex 서브에이전트**였다(`thread_spawn`, depth 1, nickname `Dewey`). 확장 안에 Codex 를 보는 눈이 둘(`providers/codex/` = rollout, `providers/codexRescue/` = `.log/`)이고 **서로 안 겹친다**는 것을 여기서 확인했다.

### 1-2. 세 모드 구조를 사용자에게 확인받는 과정에서 정정 1건

사용자가 "세 모드 모두 Claude 요청서 → Codex 작업 → 문서 → Claude 정제 맞지?"라고 물었다. **REVIEW 만 다르다** — 요청서가 없고(대상이 git diff), Codex 도 파일을 못 쓴다(`codex exec review` 는 read-only 고정). `send.sh` 가 `-o` 회수분을 `_review_` 로 저장한다. 부수적으로 REVIEW 에는 `stale` 판정이 없다.

### 1-3. 핑퐁(CHAT) 모드 신설

`codex exec resume [SESSION_ID] [PROMPT]` 의 존재를 확인하고 2턴 실측으로 맥락 유지를 검증했다(6.5초). 배관 재사용 가능 여부가 핵심이었는데 `--json`·`-o`·`-m`·`-c` 를 모두 받는다. 없는 것은 `-s`·`-C` 둘뿐이고, 그건 `codex exec review` 가 이미 같은 처지라 새로운 제약이 아니었다.

설계는 **기존 배관을 하나도 타지 않는 별도 경로**로 잡았다(스크립트 맨 앞에서 분기 후 조기 종료). 락·marker·baseline·변경 감지·`status.json`·heartbeat 를 전부 건너뛴다. 그 결과 기존 세 모드에 회귀가 없고, `.log/` 에 안 쓰므로 **확장 코드를 한 줄도 고치지 않고** 진행 패널에서 빠졌다 — 사용자의 "코덱스 패널은 건들지마" 지시와 정확히 맞물렸다.

### 1-4. Codex CONSULT 검토가 실제 결함을 잡았다

요청서([260822_143259](../codex_rescue/260822_143259_request_chat-mode-design.md))에 설계가 딛고 선 판단 5개를 가설로 명시하고 "이걸 먼저 의심하라"고 걸었다. 읽을 범위를 `send.sh:50-247` + `SKILL.md:258-341` 로 못 박아 탐색을 막았다(레포 전수는 20분이 걸린다는 실측이 있다).

결과는 §3 참조. **기각한 지적이 하나도 없었다.**

### 1-5. 상태바 메뉴 한 줄화

사용자가 스크린샷에 화살표로 짚은 것은 전부 `detail`(둘째 줄)이었다. 4개 항목에서 제거하고, 정보가 필요한 곳은 label 로 올렸다 — `워크플로우 보기` → `워크플로우 패널`. "창 다시 로드"는 label 에서 빼고 description 끝에 한 마디만 남겼다(창이 예고 없이 리로드되는 건 경고할 값어치가 있다).

### 1-6. Codex 채팅 패널 신설

데이터 소스가 진행 패널과 다르다 — `.log/` 가 아니라 **대화 문서 자체**다. 카드 = 대화, 최근 것이 펼쳐진 채로 열린다. `⚠️ 스레드 끊김`·`⏹ 새 대화로 전환`도 그대로 그린다(왜 맥락이 바뀌었는지 안 보이면 문서를 읽는 의미가 없다).

## 3. 시행착오

### 3-1. 🔴 "read-only 는 상속된다"고 가정했다 — 틀렸다

- **잘못된 가정**: `codex exec resume` 에 `-s` 가 없으니 첫 턴의 `-s read-only` 가 이어질 것이다. SKILL.md 에 "Codex 는 어떤 파일도 쓰지 못한다"고 적기까지 했다
- **발견 경위**: Codex 가 이 지점을 **P1·확신도 "낮음"**("코드만으로는 확정 불가")으로 표시했다. 실측했더니 resume 턴에서 **파일이 실제로 만들어졌다**
- **복구**: `-c sandbox_mode="read-only"` 로 강제. 전후 대조로 뚫림→차단 확인
- **교훈**: CHAT 은 변경 감지를 통째로 뺐으므로, 이 구멍은 **아무도 못 잡는 상태**였다. 안전 전제를 문서에 쓰기 전에 실측해라. Codex 가 "확정 불가"로 표시한 지점이 가장 위험한 지점이었다

### 3-2. `--new` 실패가 옛 스레드를 되살린다

- **잘못된 가정**: `--new` 는 새 문서를 만드니 이전 것과 무관하다
- **발견 경위**: Codex 의 P0 지적. 코드로 확인 — 새 턴이 실패하면 새 문서가 안 생기고, 다음 호출이 glob 으로 **이전 문서를 찾아 그 thread_id 를 재개**한다
- **복구**: codex 호출 **전에** 이전 세대를 닫는다(thread_id 비우기 + `⏹` 기록 + 되읽어 검증)
- **교훈**: "버린다"는 결정은 **버리기 전에** 영속화해야 한다

### 3-3. "workspace.fs 로는 홈 디렉토리를 못 읽는다"고 말했다 — 틀렸다

- **잘못된 가정**: 홈은 워크스페이스 밖이라 `vscode.workspace.fs` 로 접근이 안 된다
- **발견 경위**: 사용자가 "무슨 말이야, 접근이 안 된다고?"라고 되물었다. 확인해 보니 **이 프로젝트가 이미 하고 있었다** — [discovery.ts:24](../../src/providers/codex/discovery.ts#L24) 가 `folder.uri.with({ path: '/home' })` 로 원격 홈을 읽는다
- **교훈**: `workspace.fs` 는 워크스페이스 안/밖이 아니라 **URI** 로 동작한다. authority 만 유지하면 어디든 읽는다. 내 프로젝트에 이미 있는 코드를 확인하지 않고 단정했다

### 3-4. 구형 대화 문서가 파싱되지 않았다

이모지(`✳️`/`🔷`)를 도입한 건 CHAT 신설 몇 시간 **뒤**였다. 그 전에 만든 문서 2건은 `**클로드**` 만 있어, 파서가 speaker 를 못 찾고 **대화 전체를 코덱스 발언으로** 붙였다. 이모지 없는 형태도 인식하는 폴백을 넣었다(`findSpeaker`). 실제 문서 3종으로 검증.

## 4. 발견한 코드베이스 함정

### 4-1. 🔴 패널 게이트가 **로컬 홈만** 본다 (미수정, 별도 트랙)

[extension.ts:2871](../../src/extension.ts#L2871) `codexRescueSkillInstalled()` 이 `os.homedir()` + node `fs` 를 쓴다. 확장이 `extensionKind: ui` 라 **항상 로컬 PC 의 홈**을 본다. 그런데 원격 창에서 스킬이 실제로 필요한 곳은 **원격 서버의 `~/.claude/skills/`** 다.

| 로컬 | 원격 | 증상 | 심각도 |
|---|---|---|---|
| 有 | 無 | 메뉴는 뜨는데 "0건" | 낮음 |
| **無** | **有** | **메뉴가 아예 안 뜸** — 쓸 수 있는데 뷰어를 못 찾음 | 이게 손실 |

2차 게이트(`workspaceUsesCodexRescue`)는 `workspace.fs` 라 원격을 정확히 본다. 어긋나는 건 1차뿐이다.

**고칠 때 반드시 함께 할 것 3가지**:
1. 비동기 전환 — 호출부 3곳([467](../../src/extension.ts#L467)·[775](../../src/extension.ts#L775)·[2982](../../src/extension.ts#L2982)), 그중 775 는 `activate` 경로
2. `remoteHomeCandidates()`([discovery.ts:21](../../src/providers/codex/discovery.ts#L21)) 재사용 — 새로 짤 것 없음
3. 🔴 **캐시 필수** — 2982 는 `syncCodexRuns()` 안이고 **2초마다 돈다.** 그냥 원격으로 바꾸면 2초마다 SSH 왕복 + `/home` 디렉토리 읽기가 된다. 스킬 설치/제거는 창 생명주기에 몇 번 없으므로 activate 1회 + 명시적 갱신으로 충분하다

지금 환경(로컬 + 서버 4대 전부 배포)에서는 두 케이스 다 발생하지 않아 무증상이다.

### 4-2. `codex exec resume` 의 제약

- `-s`(샌드박스) **없음** → `-c sandbox_mode=...` 로 우회. **상속되지 않는다**(§3-1)
- `-C`(작업 디렉토리) **없음** → 미리 `cd`. `codex exec review` 와 같은 처지
- `--json`·`-o`·`-m`·`-c`·`--skip-git-repo-check` 는 **받는다**
- `[SESSION_ID]` 는 UUID **또는 thread name** 을 받는다(이름 붙이는 경로는 미탐색)

### 4-3. CHAT 속도는 배관이 아니라 질문의 무게가 정한다

같은 배관에서 `1+1은?` = **7초**, 항목 4개짜리 설계 질문 = **2분 20초**. `-C`(작업 디렉토리 지정)는 무관함을 대조로 확인했다(짧은 질문 + `-C` = 7초). 그래서 SKILL.md 에 "한 번에 하나만, 파일 읽지 마라를 붙여라, 무거우면 CONSULT"를 규칙으로 박았다.

### 4-4. Bash 도구 타임아웃(3분)에 걸려도 실행은 끝나 있을 수 있다

실측: 답이 도착하고 대화 문서까지 기록된 **직후**에 잘렸다. 락은 그때도 정상적으로 풀렸다. **타임아웃 = 실패로 단정하지 말고 대화 문서부터 확인해라.**

### 4-5. 마켓 반영은 게시 후 8분쯤

CI 가 `Published ... v1.11.0` 을 찍고 나서도 마켓 API 는 한동안 옛 버전을 준다. 이번엔 게시 06:46:24Z → 반영 06:54:42Z. 1.10.1 때도 8분이었다(20:50:56 → 20:58:56). **CI 성공 직후의 API 조회로 실패 판정하지 마라.**

### 4-6. `/skill_cp_install deploy` 는 vault 가 갈라지면 중단된다

이번에 실제로 발생했다(`! [rejected] main -> main (fetch first)`). 커밋은 로컬에 남고 배포가 멈춘다. `cd /f/Obsidian && git pull --rebase && git push` 후 재실행하면 된다. **`--force` 를 쓰지 마라** — 스크립트도 그렇게 경고한다.
