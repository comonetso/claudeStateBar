## 1. 작업 흐름

### 1-1. 원래 문제 — 순차 배치 워크플로우에서 비프 배치마다 오발
- 워크플로우가 에이전트를 순차 배치(parallel 4 → parallel 2 → 검증)로 돌리면 **배치가 끝날 때마다** 완료 비프가 울림.
- 원인: workflow `journal.jsonl`엔 에이전트별 `started`/`result`만 있고 "스크립트 전체 종료" 마커가 없음 → 배치 사이 공백에 "지금까지 started된 게 전부 done" = all-done 오판.

### 1-2. 방식 A 구현 (v1.7.48 1차) — 세션 JSONL 통지 게이트
- 진짜 완료 신호를 부모 세션 JSONL의 `<task-notification><status>completed</status>`로 보고, `getCompletedWorkflowIds()` + 완료 비프 루프 게이트 삽입. journal all-done이어도 통지 없으면 억제.
- 문서(CHANGELOG/README 영·한) + package 1.7.48 + 빌드/설치까지 진행.

### 1-3. 회귀 — 비프가 아예 안 울림 (무음)
- 검증 워크플로우 3회(34초/112초/169초) 전부 무음. 사용자 "이전엔 잘 났다" → 내 수정이 회귀.
- 출력로그로 `[wf-done] … no completion notice yet — batch gap, suppress` 반복 확인 → 게이트가 최종 완료까지 억제 중.
- **내 오진**: "task-notification flush가 사용자 턴에야 일어나 폴링 시점엔 통지가 없다"고 진단. (틀림 — 아래 §3)

### 1-4. Codex 교차검증 — 진짜 원인 + 더 나은 신호
- 사용자 지시로 Codex에 복붙 프롬프트 전달. Codex가 **확정 결함**을 잡음: `src/extension.ts` `taskToWf.set(tid[1], wid[2])` — 정규식 캡처 그룹이 1개뿐이라 wfId는 `wid[1]`, `wid[2]`는 항상 `undefined` → 매핑 전멸 → `getCompletedWorkflowIds`가 **항상 빈 집합** → 모든 워크플로우 억제.
- Codex가 **더 나은 완료 신호**도 발견: `<sessionDir>/workflows/<wfId>.json` — 워크플로우 런 최종 결과 레코드.

### 1-5. 마커 기반 재설계 (v1.7.48 최종)
- `readWorkflowTerminalStatus()` 신설: `workflows/<wfId>.json` 최상위 `status` 파싱.
- 완료 비프 루프: **1차** 마커 `status==='completed'` → 비프 / `failed`·`killed` → 게이트 닫고 무음 / **2차** 마커 없으면 wid[1] 고친 통지 파서 fallback / 둘 다 없으면 배치 공백으로 억제.
- **경쟁조건 방어**: await 후 `alertedWorkflowDone.has(key)` 재확인 → set (has→set 사이 await 없어 원자적). refresh 겹침 시 중복 비프 방지.
- 실측 성공: `[wf-done] all 4 agents done for wf_147f32fa-323 → beep` 1회 + 소리 재생 + 이후 폴링 중복 없음 + 배치공백(39초) 억제.

## 3. 시행착오
- **잘못된 가정**: 비프 무음의 원인이 "task-notification flush 지연"이다.
  - **발견 경위**: Codex가 지적 — 로그의 "no completion notice"는 wid[2] 버그로 통지가 있어도 매핑이 실패해 항상 찍힌 것. flush 지연은 이 로그로 **미확정**. 진짜 원인은 캡처 인덱스 오류.
  - **복구**: wid[2]→wid[1] + 마커 기반 1차 신호.
  - **교훈**: 파서 정확성은 grep으로 "별도 재현"하지 말고 **실제 코드 로직 그대로** 돌려봐야 한다. 나는 grep 재현으로 "게이트 통과"라 오판하고 `wid[2]`를 여러 번 읽고도 못 잡았다.

## 4. 발견한 코드베이스 함정
- **`<sessionDir>/workflows/<wfId>.json`** = 워크플로우 런 전체의 최종 결과 마커. 최상위 `status`는 `completed`|`failed`|`killed`(로컬 46건 실측: 40/1/5). **완료 즉시 디스크에 기록**(mtime=마지막 에이전트 종료 시각)이라 세션 JSONL 통지보다 신뢰. `findWorkflowsForSession()`은 `workflows/scripts`는 읽지만 이 파일은 안 읽고 있었음.
- **`pass` status는 최상위가 아님** — 검증류 워크플로우가 `result` 내부에 담는 값. 최상위 `status`만 파싱하면 안 걸림(성공은 `completed`만 보면 됨).
- **정규식 캡처 인덱스**: `/Run ID: (wf_[A-Za-z0-9-]+)/`는 그룹 1개 → wfId는 `[1]`. `[2]`는 항상 undefined.
- **task-notification 세션 JSONL 기록 시점**은 공식 디스크 계약이 없음 → 실시간 완료 신호로 쓰면 위험(Codex). 마커 파일이 안전.
- **refreshAllSessions 겹침**: 같은 초에 interval/watcher가 동시 호출될 수 있음 → 완료 판정에 await가 끼면 두 refresh가 통과해 중복 비프 가능. per-key 재확인(has→set 원자) 필요.
