## 무엇을 만들었나 — CHAT(핑퐁) 모드

기존 세 모드(CONSULT / REVIEW / EDIT)는 전부 **"한 번 무겁게 던지고 오래 기다린다"** 이다.
요청서를 길게 쓰고, 백그라운드로 던지고, 1분 25초~20분 뒤에 문서로 받는다.

사용자의 불만은 **"한 덩어리가 너무 무겁다"** 였다. 대화 중에 "코덱스, 넌 어떻게 생각해?"를
가볍게 던지고 그 자리에서 받고 싶다는 것이다. 그래서 만든 것이 CHAT 이다.

```bash
send.sh --chat --slug <슬러그> [--subject "<한 줄>"] [--new] <던질 말>
```

- 첫 턴은 `codex exec --json -s read-only -C <root> -o <tmp>`, 이후 턴은
  `codex exec resume <thread_id> --json -o <tmp>`
- `thread_id` 는 대화 문서 frontmatter 에 박아 두고 다음 턴에 `sed` 로 읽는다
- 슬러그가 곧 **대화 스레드 식별자**다. 같은 슬러그로 다시 부르면 이어지고, `--new` 면 새로 시작
- 대화 문서(`<스탬프>_chat_<슬러그>.md`)에 턴마다 `클로드` / `코덱스` 를 append
- Claude 는 이걸 **동기로** 호출하고(다른 모드는 백그라운드), 받은 답을 채팅창에 바로 옮긴다

## 내(Claude)가 세운 가설과 근거     ← 이걸 먼저 의심해줘

다섯 개의 판단으로 이 설계가 서 있다. 각각 틀렸을 수 있다.

1. **스크립트 맨 앞에서 갈라져 기존 배관을 하나도 안 타게 한 것이 맞다.**
   근거: 락·marker·baseline·변경 감지·`status.json`·heartbeat 를 전부 건너뛰고 조기 종료하면
   기존 세 모드에 회귀가 안 생긴다. 실제로 REVIEW dry-run 으로 회귀 없음을 확인했다.
   의심: 공통 로직이 두 벌이 된 것 아닌가? 나중에 한쪽만 고쳐 어긋날 위험은?

2. **read-only 로 고정하고 변경 감지를 통째로 뺀 것이 맞다.**
   근거: Codex 에게 쓰기 권한이 없으면 감지할 변경이 원리적으로 생기지 않는다. 응답은 `-o` 로
   회수해 스크립트가 쓴다(REVIEW 와 같은 구조).
   의심: `-s read-only` 만으로 정말 쓰기가 봉쇄되나? 우회 경로가 있나?

3. **`.log/` 에 이벤트를 안 써서 진행 패널에 안 뜨게 한 것이 맞다.**
   배경: 같은 저장소의 VS Code 확장이 `.log/<스탬프>_events.jsonl` 과 `_status.json` 을 읽어
   진행 카드를 그린다. 핑퐁은 10초짜리라 카드가 쌓이면 방해만 된다. 사용자 지시로 확장 코드는
   건드리지 않기로 했고, **안 쓰면 애초에 안 보인다**는 방식을 골랐다.
   의심: 나중에 "핑퐁도 보고 싶다"가 되면 되돌리기 어려운 구조인가?

4. **실패하면 스레드를 폐기하는 것이 맞다.** (이건 네가 이미 지적해서 반영한 것이다)
   구현: 응답이 비면 실패 턴을 기록하지 않고, 문서의 `thread_id` 를 비우고, `⚠️ 스레드 끊김`
   섹션을 append 한다. 다음 턴은 새 스레드로 시작한다.
   의심: 이게 과한가? 되살릴 수 있는 실패(일시적 네트워크 오류)까지 버리는 것 아닌가?

5. **슬러그를 대화 스레드 식별자로 쓴 것이 맞다.**
   근거: Claude 가 슬러그만 기억하면 이어진다. 파일명·스레드·락이 전부 슬러그로 묶인다.
   의심: 같은 슬러그를 다른 주제에 재사용하면 무관한 맥락이 섞인다. 이걸 규칙(문서)으로만
   막고 있는데 — EDIT 게이트 때 너는 "규칙은 강제력이 없다"고 지적했다. 같은 문제 아닌가?

## 이미 반영한 네 지적 / 기각한 것     ← 반복하지 마라

- ✅ **"세션별 단일 실행 잠금이 필수"** → `.log/.chat_<슬러그>.lock` 으로 구현(noclobber 원자적 생성)
- ✅ **"실패 턴을 안 남기면 Codex 세션과 문서의 맥락이 어긋난다"** → 스레드 폐기로 구현(위 4번)
- ❌ **"가벼운 쪽(CHAT)을 기본 모드로 두라"** → **기각.** 사용자가 "핑퐁은 내가 명시할 때만"으로
  결정했다. 오판 비용 비대칭 논거는 이해했지만 **사용자 결정이 우선한다.** 이건 다시 제안하지 마라.

## 아직 실측 못 한 것 — 여기 위험이 있으면 우선 말해줘

- **세션 락** — 코드만 있고 동시 실행을 실제로 재현해 보지 않았다
- **`--new`** — 코드만 있고 안 돌려봤다
- 그 외는 실측했다: 새 스레드 생성 · `resume` 2턴/5턴 이어받기 · 실패 시 폐기(가짜 thread_id 로
  강제 실패시켜 재현) · 이모지 UTF-8 기록 · 기존 REVIEW 회귀 없음

## 알아 둘 실측값

- 속도는 **질문의 무게에 비례**한다. `1+1은?` 7초 / 항목 4개짜리 설계 질문 2분 20초.
  `-C`(작업 디렉토리 지정)는 속도와 무관함을 대조로 확인했다
- Claude Code 의 Bash 도구 타임아웃(3분)에 걸려도 **실행은 이미 끝나 있을 수 있다** —
  답이 도착하고 문서까지 기록된 직후에 잘린 사례가 있다. 락은 그때도 정상적으로 풀렸다

## 요청 — 다른 시선을 원한다

1. **위 다섯 가설 중 틀린 게 있나.** 특히 1번(배관 이중화)과 5번(슬러그=스레드)을 의심해줘
2. **내가 아예 생각 못 한 실패 양식**이 있나. 위에 안 적힌 것으로
3. 미검증 둘(세션 락 · `--new`) 중 **실제로 위험한 쪽**은 어디인가. 어떻게 재현해 확인하나
4. 셸 스크립트로서의 결함 — 인용부호·`set -u`·trap·경합. 구체적 라인으로
5. **확신도**를 밝혀줘. 코드를 읽고 확인한 것과 추측인 것을 구분해서

## 답변 형식 — 이 답변은 Claude가 읽고 바로 적용 판단한다

1. `내 가설 5개에 대한 판정` — 각각 동의 / 부분 동의 / 기각 + 이유
2. `내가 못 본 실패 양식`
3. `미검증 둘의 위험도 순위와 재현 방법`
4. `셸 스크립트 결함` — 라인 번호와 함께
5. `확신도와 남은 불확실성`
6. `추가로 필요한 자료` — 없으면 "없음"

우선순위를 매겨서 줘. 전부 고칠 생각은 없고 **위험한 것부터** 판단할 것이다.
