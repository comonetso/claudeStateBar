# CHAT(핑퐁) 모드 설계 재검토

우선순위부터 말하면 다음 세 가지가 먼저다.

1. **P0 — Codex 세션과 대화 문서 사이에 트랜잭션 경계가 없다.** Codex가 턴을 받아들인 뒤 문서 append 전에 신호·타임아웃·디스크 오류가 나면, 세션만 전진하고 문서는 이전 `thread_id`를 그대로 가진다. 다음 호출은 어긋난 세션을 자동 재개한다.
2. **P0 — `--new`가 영속적인 전환이 아니다.** 새 턴이 실패해 새 문서가 생기지 않으면, 다음 일반 호출은 다시 이전 문서의 이전 스레드를 재개한다.
3. **P1 — `read-only`는 Codex 샌드박스 정책이지 이 셸 전체의 무부작용 보장이 아니다.** 래퍼는 실제로 `.log`와 대화 문서를 쓰며, 경로가 심볼릭 링크인 경우 프로젝트 밖 쓰기로 이어질 수 있다. `resume`의 read-only 상속도 이 코드만으로는 확정할 수 없다.

따라서 현재 설계를 폐기할 필요는 없지만, **“응답 파일이 비었을 때만 실패”라는 상태 모델은 부족하다.** 가장 먼저 `in-flight → committed/broken` 상태를 내구성 있게 만들고, 그 다음 `--new`와 락 소유권을 보강하는 편이 맞다.

## 1. 내 가설 5개에 대한 판정

### 1) 앞에서 갈라져 기존 배관을 타지 않는다 — **부분 동의**

진행 카드·heartbeat·대규모 변경 감지를 CHAT에 강제로 태우지 않은 결정은 목적에 맞다(`send.sh:50-66`, `SKILL.md:324-333`). 조기 분기 자체도 기존 세 모드의 동작 회귀 면적을 줄인다.

다만 “배관을 공유하지 않는다”와 “공통 안전 장치까지 별도 구현한다”는 같은 말이 아니다. CHAT 안에는 임시 디렉터리, Windows 경로 변환, 모델/샌드박스 옵션, Codex 실행, 종료 코드 판정, 신호 정리 같은 저수준 실행 배관이 다시 생겼다(`send.sh:108-160`). 향후 CLI 옵션이나 Windows sandbox 정책이 바뀌면 한쪽만 고쳐질 가능성이 있다.

권장 방향은 CHAT을 기존의 **진행 상태 배관**에 합치는 것이 아니라, 다음처럼 저수준 함수만 공통화하는 것이다.

- Codex 공통 인자 조립 및 Windows 경로/샌드박스 적용
- 임시 작업공간과 자식 프로세스 수명 관리
- JSON 이벤트에서 `thread_id`와 턴 최종 상태를 읽는 부분
- 원자적 문서 갱신 및 오류 판정

즉, 조기 분기는 유지하되 실행 안전성만 한 벌로 두는 것이 좋다. 지정 범위 밖 기존 배관은 읽지 않았으므로 실제 중복량에 대한 확신도는 중간이다.

### 2) read-only 고정이므로 변경 감지를 뺀다 — **부분 동의**

무거운 저장소 전체 변경 감지를 빼는 것은 동의한다. 첫 턴에는 실제로 `-s read-only`가 붙는다(`send.sh:139-142`). 그러나 “Codex가 어떤 파일도 쓰지 못한다”는 설명(`send.sh:209-210`)은 보안 경계를 너무 넓게 표현한다.

- 이어받기는 `-s read-only` 없이 실행되며(`send.sh:137-142`), 첫 턴 정책이 정말 그대로 상속된다는 전제에 의존한다. 코드만으로는 Codex CLI 0.145.0의 실제 유효 정책을 확인할 수 없다.
- 래퍼 자체는 `.log/.gitignore`, 락, 대화 문서를 쓴다(`send.sh:92-110`, `197-232`). 이는 의도된 쓰기지만 Codex 샌드박스와 별개의 권한이다.
- `CH_DOCS` 또는 기존 `CH_DOC`가 심볼릭 링크이면 래퍼의 redirection/append가 링크를 따라 프로젝트 밖의 사용자 쓰기 가능 파일을 건드릴 수 있다(`send.sh:93-100`, `116-127`, `175-232`). 신뢰한 저장소만 대상으로 하면 가능성이 낮지만 Linux 서버까지 배포한다면 경계를 명시하거나 링크를 거부해야 한다.
- 로컬 MCP나 외부 서비스 도구가 활성화돼 있다면, 파일시스템 read-only가 외부 부작용까지 막는다고 볼 수 없다. 이것은 제공된 코드만으로 확인할 수 없는 조건부 위험이다.

따라서 문구는 “Codex의 **샌드박스 적용 파일 도구**는 read-only이며, 래퍼만 지정된 대화 산출물을 쓴다” 정도가 정확하다. 전체 변경 감지를 되살릴 필요는 없지만, 첫 턴과 resume 각각에서 실제 sandbox 정책을 한 번 실측하고, 문서 경로의 실경로·심볼릭 링크 여부는 싸게 검증하는 편이 좋다.

### 3) `.log/` 이벤트를 안 써 진행 패널에서 숨긴다 — **동의**

패널이 `_events.jsonl`과 `_status.json`을 기준으로 그려진다는 주어진 전제에서는 단순하고 결합도가 낮은 선택이다(`send.sh:58-62`, `SKILL.md:326-333`). 나중에 표시하고 싶어져도 CHAT 전용 이벤트를 선택적으로 발행하면 되므로 되돌리기 어려운 구조도 아니다.

다만 **패널 비노출과 운영 관측성 부재를 묶을 필요는 없다.** 현재 락은 빈 파일이라 PID·시작 시각·호스트·소유 토큰이 없고(`send.sh:99-105`), stale인지 판단하려면 사람이 프로세스를 찾아야 한다. 확장이 읽지 않는 이름의 작은 상태/락 메타데이터를 남겨도 패널에는 뜨지 않는다. 이 메타데이터는 특히 여러 PC·서버 배포에서 유용하다.

### 4) 실패하면 스레드를 폐기한다 — **부분 동의**

세션이 사용자 턴을 받았는지 확정할 수 없는 실패라면, 맥락 보존보다 문서/세션 일치를 우선해 폐기하는 판단은 맞다. 일시적 네트워크 오류라고 무조건 되살리면 안 된다.

그러나 현재 구현은 “실패”를 `CH_LAST`가 비었는지 하나로만 판정한다(`send.sh:160-168`). 다음 실패들은 폐기 경로에 들어가지 않는다.

- 종료 코드가 0이 아닌데 `CH_LAST`가 일부라도 있는 경우
- Codex가 턴을 받은 뒤 셸이 HUP/INT/TERM 또는 상위 도구 타임아웃으로 종료된 경우
- 새 문서 헤더 작성 후 첫 턴 append가 실패한 경우
- 기존 문서 append가 부분적으로 실패한 경우
- 실패 분기의 `sed -i`가 실패했지만 오류가 무시된 경우

반대로 이벤트가 “요청이 세션에 들어가기 전에 실패했다”는 것을 확실히 증명한다면 기존 스레드를 버리지 않아도 된다. 권장 판정은 `CH_RC`, 최종 이벤트(`turn.completed`/실패 이벤트), 최종 응답 존재를 함께 보는 것이다. **이벤트로 안전을 증명할 수 없으면 폐기**하는 보수성은 유지하는 편이 맞다.

### 5) 슬러그를 대화 스레드 식별자로 쓴다 — **부분 동의(명칭은 기각)**

슬러그는 사람이 기억하는 키로는 좋지만, 현재 구현에서 스레드 식별자 자체는 아니다. `--new`를 쓸 때 같은 슬러그로 여러 문서와 여러 `thread_id`가 생기며, 코드는 파일명상 가장 마지막 문서를 골라 재개한다(`send.sh:114-127`). 즉 슬러그는 정확히는 **“최신 대화 세대를 가리키는 변경 가능한 별칭”**이다.

이 차이 때문에 다음 문제가 생긴다.

- 같은 슬러그를 다른 주제에 재사용해도 기계적 거부가 없다. 문서 규칙만으로 막고 있어 지적한 대로 강제력이 약하다(`SKILL.md:265-267`).
- `--new` 실패 시 최신 세대가 만들어지지 않아 별칭이 이전 스레드로 되돌아간다.
- 대화 문서가 다른 머신으로 복제되는 경우, 최신 문서의 `thread_id`가 그 머신의 로컬 Codex 저장소에 없을 수 있다. 5대 배포 환경에서는 확인해야 할 실제 경계다.
- 서로 다른 슬러그 문서에 같은 `thread_id`가 복제되면 락은 슬러그별이라 같은 실제 세션을 동시에 resume할 수 있다.

슬러그를 버릴 필요는 없다. 첫 문서에 `generation_id`, `session_origin`(호스트/Codex home 식별), 정규화한 subject를 두고, 기존 슬러그의 subject가 달라지면 `--new` 또는 새 슬러그를 요구하는 식으로 보강하면 된다. resume 시에는 슬러그 락뿐 아니라 실제 `thread_id` 기준 중복도 막는 편이 안전하다. 문서에는 “슬러그=스레드 ID” 대신 “슬러그=현재 대화 세대의 별칭”이라고 쓰는 것이 구현과 일치한다.

## 2. 내가 못 본 실패 양식

### P0. Codex 세션 전진과 문서 기록 사이의 크래시 간격

가장 큰 구멍이다. Codex 호출은 `send.sh:160`에서 끝나고 문서 기록은 `197-232`에서 일어난다. 그 사이 또는 append 도중에 신호·프로세스 강제 종료·디스크 부족·권한 오류가 발생하면 Codex 세션에는 새 사용자 턴(어쩌면 답까지)이 남지만 문서에는 없다. 기존 문서의 `thread_id`는 살아 있으므로 다음 호출은 그 세션을 그대로 이어간다.

신호 trap도 임시 디렉터리와 락만 지운다(`send.sh:110-112`). 문서의 스레드를 `broken`으로 바꾸지 않고, 자식 Codex가 정말 끝났는지 확인하지도 않는다. 상위 Bash 도구의 타임아웃이 셸만 종료하고 자식 프로세스를 남기는 형태라면, 락을 푼 뒤 이전 Codex가 계속 도는 경합도 가능하다.

수정 원칙은 다음과 같다.

1. Codex 호출 전에 문서 또는 CHAT 전용 상태에 `in_flight`를 내구성 있게 기록한다.
2. 응답과 완료 이벤트가 확인되면 문서 전체를 임시 파일에 완성한 뒤 같은 디렉터리에서 원자적으로 교체하고 `committed`로 바꾼다.
3. 다음 실행이 `in_flight`를 발견하면 자동 resume하지 말고, 이벤트로 완료를 회수할 수 있을 때만 복구한다. 그 외에는 이전 thread를 `broken` 처리한다.
4. trap은 자식 PID를 알고 신호를 전달한 뒤 `wait`하여 자식 종료를 확인하고, 그 다음에만 락을 푼다. SIGKILL은 trap으로 복구할 수 없으므로 다음 실행의 `in_flight` 복구가 필요하다.

### P0. `--new` 첫 턴 실패 후 이전 스레드 부활

`--new`이면 기존 문서를 찾고도 thread를 읽지 않은 뒤 새 파일명을 계산한다(`send.sh:114-127`). 그러나 새 Codex 실행이 빈 응답으로 실패하면 새 파일은 존재하지 않아 실패 분기가 아무 문서도 바꾸지 않는다(`168-193`). 다음 일반 호출은 다시 이전 문서를 최신 문서로 찾아 이전 thread를 resume한다.

`--new`의 “기존 맥락을 버린다”는 결정을 Codex 호출 전에 영속화해야 한다. 예를 들어 새 세대의 `in_flight` 문서/상태를 먼저 만들거나, 이전 문서에 `superseded_by`/`closed`를 원자적으로 기록해야 한다. 새 턴 실패 뒤에도 자동으로 이전 세대로 되돌아가면 안 된다.

### P1. 실패 처리 자체가 실패해도 성공처럼 보고

기존 문서의 `thread_id`를 비우는 `sed -i`와 끊김 섹션 append의 오류가 모두 버려진다(`send.sh:175-185`). 특히 `sed -i`가 실패하면 thread가 그대로인데도, 아래에서는 파일이 존재한다는 이유만으로 “스레드를 폐기했다”고 출력한다(`186-193`).

스레드 폐기는 원자적 문서 교체로 수행하고, 다시 읽어 `thread_id`가 비었거나 상태가 `broken`인지 검증한 뒤에만 그렇게 보고해야 한다. 실패하면 성공 문구 대신 수동 개입이 필요한 별도 오류로 끝내야 한다.

### P1. 비정상 종료 코드 + 비어 있지 않은 답을 정상 성공으로 승격

`CH_RC`는 저장하지만 실패 조건에는 쓰지 않는다(`send.sh:160-168`). `CH_LAST`만 비어 있지 않으면 문서에 기록하고 마지막에 항상 `exit 0` 한다(`234-245`). 따라서 부분 출력 후 CLI가 실패한 경우 Claude 호출자는 성공으로 받는다.

`CH_RC != 0`이면 최소한 degraded 상태로 기록하고 비정상 종료해야 한다. 해당 턴을 안전하게 resume할지는 JSON 이벤트의 최종 상태로 정해야 한다. 단지 텍스트가 있다는 이유만으로 `committed`로 보면 안 된다.

### P1. 머신 간 문서 이동과 로컬 thread의 수명 불일치

문서가 Git 등으로 다른 PC/서버에 전달되면 그 안의 `thread_id`도 전달된다. Codex의 resume 저장소가 머신/Codex home별이라면 다른 머신에서 같은 슬러그를 호출할 때 타 머신 thread를 재개하려다 실패한다. 현재 문서에는 origin 정보가 없어 정상적인 로컬 대화와 구별하지 못한다.

`session_origin`을 기록해 다르면 자동으로 새 세대를 만들도록 해야 한다. 이 위험은 배포 형태상 중요하지만, Codex 0.145.0 thread가 실제로 어느 범위에서 공유되는지는 제공된 자료만으로 확정하지 않았다.

### P1. 신뢰하지 않은 경로의 심볼릭 링크를 래퍼가 따라감

Codex 자체가 read-only여도 셸 redirection은 샌드박스 밖에서 동작한다. 기존 chat 문서나 `docs/codex_rescue`가 링크이면 append가 링크 대상에 쓰일 수 있다. 경로의 각 구성요소가 실제 프로젝트 아래인지 확인하고, 기존 chat 문서가 일반 파일인지 확인해야 한다. 새 문서도 단순 `>`보다 안전한 임시 파일 생성 후 원자적 rename을 써야 한다.

### P2. frontmatter 주입과 parser 오염

`--subject`는 임의 문자열인데 YAML escaping 없이 한 줄로 쓴다(`send.sh:203`). subject에 줄바꿈, `---`, `thread_id:`가 들어가면 frontmatter가 깨지고, 다음 호출의 `sed ... | head -1`이 공격자가 넣은 첫 `thread_id`를 읽을 수 있다(`120-121`). subject를 JSON/YAML 안전 인코딩하거나 줄바꿈 없는 제한된 값으로 검증해야 한다.

### P2. 대화 본문이 턴 카운터를 속임

턴 수는 문서 전체에서 `^## [0-9]*턴 `을 세어 계산한다(`send.sh:214-215`). 사용자 질문이나 Codex 답변이 같은 모양의 Markdown 제목을 포함하면 다음 턴 번호가 틀어진다. 턴 수를 frontmatter의 구조화 필드로 관리하거나, 본문과 충돌하지 않는 내부 marker만 세어야 한다.

### P2. Windows/Linux에서 슬러그 대소문자 의미가 다름

문서는 lowercase kebab-case를 요구하지만 코드는 대문자도 허용한다(`send.sh:86-89`, `SKILL.md:265`). Windows의 보통 파일시스템에서는 `Foo`와 `foo`가 같은 경로로 취급되고 Linux에서는 다를 수 있다. 여러 머신에 배포한다면 `[a-z0-9-]`로 강제하고 선두/후미/연속 하이픈 정책도 한쪽으로 통일하는 것이 좋다.

### P2. CRLF frontmatter와 취약한 JSON 정규식

다른 Windows checkout에서 문서가 CRLF로 바뀌면 `^---$`가 닫는 구분자를 못 잡거나 추출된 thread에 `\r`이 붙을 수 있다(`send.sh:120-121`). 또한 thread 추출은 공백 없는 정확한 JSON 조각 `"thread_id":"..."`만 인정한다(`163-166`). CLI JSON 서식이 공백을 넣는 정도로 바뀌어도 이어받기가 조용히 끊긴다. CR 제거와 실제 JSON parser 사용이 낫다.

## 3. 미검증 둘의 위험도 순위와 재현 방법

### 1위 — `--new`: **높음, 코드로 결함 확인됨**

정상 성공만 확인하면 부족하다. 다음 두 시나리오를 별도의 폐기 가능한 슬러그에서 시험해야 한다.

**정상 전환 시험**

1. 슬러그 S로 첫 대화를 만들어 문서 A와 thread A를 기록한다.
2. 같은 S에 `--new`로 성공하는 질문을 보낸다.
3. 문서 B가 새로 생기고 thread B가 A와 다른지 확인한다.
4. `CR_DRYRUN=1`로 같은 S를 일반 호출해 `이어받기:`가 B인지 확인한다.

**실패 원자성 시험 — 현재는 실패할 것으로 판정**

1. 위의 A만 있는 상태에서 `CR_DRYRUN=1`로 일반 호출해 thread A를 확인한다.
2. `--new` 호출만 의도적으로 실패시킨다. 테스트 환경에서 존재하지 않는 `CR_MODEL`을 주어 Codex가 빈 최종 응답으로 끝나게 하는 방법이 비교적 안전하다.
3. 다시 `CR_DRYRUN=1`로 S를 일반 호출한다.
4. 현재 코드에서는 최신 새 문서가 없으므로 `이어받기:`가 thread A로 돌아갈 가능성이 아니라 **논리상 그렇게 된다.** 수정 후에는 A가 아니라 “새 세대가 실패/broken이라 자동 재개 불가”가 나와야 한다.

추가로 고정된 `date`를 쓰는 테스트 더블이나 미리 만든 동명 파일로 스탬프 충돌을 만들면, `--new`가 기존 문서에 append하고 frontmatter thread는 예전 값을 유지하는지도 확인할 수 있다(`send.sh:125-127`, `197-215`). 정상 속도에서는 드물지만 시계 역행·복원 환경까지 생각하면 막아야 한다.

### 2위 — 세션 락: **중간~높음, 기본 원자성은 타당하나 소유권/중단 복구가 부족**

`noclobber`를 이용한 같은 경로 생성은 로컬 Git Bash/일반 Linux 파일시스템에서 기본 상호배제를 제공할 가능성이 높다(`send.sh:99-106`). 다만 다음 세 시험을 분리해야 한다.

**기본 동시 실행 시험**

1. 답이 20~30초 이상 걸릴 질문을 폐기 가능한 같은 슬러그로 두 셸에서 거의 동시에 실행한다.
2. 정확히 하나만 Codex에 들어가고, 다른 하나는 즉시 nonzero와 락 오류를 내는지 확인한다.
3. 첫 실행 종료 뒤 세 번째 호출이 성공하고, 문서에 실제 성공 턴만 순서대로 있는지 확인한다.

**중단 복구 시험**

1. 한 실행이 Codex를 기다리는 동안 셸에 TERM/INT를 보낸다.
2. 자식 Codex가 남지 않았는지, 락이 풀렸는지, 문서가 `in_flight/broken`으로 남는지 확인한다.
3. TERM, 상위 도구의 180초 timeout, 강제 kill을 각각 구분한다. SIGKILL 뒤 stale lock은 예상되므로 다음 실행이 PID/host/start-time을 보고 안전하게 복구하거나 명확히 거부해야 한다.

**락 소유권(ABA) 시험 — 현재 구조의 결함 재현**

1. 긴 실행 A를 시작한다.
2. 테스트용 락을 수동 삭제하고 실행 B를 시작한다.
3. A가 끝나게 한 뒤, B가 아직 도는 동안 락 경로가 사라졌는지 본다.
4. 현재 cleanup은 소유권 확인 없이 같은 경로를 `rm -f`하므로(`send.sh:110`), A가 B의 락을 지울 수 있다. 이때 C가 들어가면 결함이 재현된 것이다.

락 파일에 임의 nonce, PID, host, 시작 시각을 쓰고 cleanup 시 nonce가 자기 것일 때만 삭제하면 ABA를 막을 수 있다. 가능하면 `mkdir` 락 디렉터리 또는 `flock` 사용 가능 범위를 검토하되, 5대 배포 파일시스템에서 실제 제공 여부를 먼저 확인해야 한다.

## 5. 확신도와 남은 불확실성

### 높음 — 제공된 코드만으로 확정

- `--new` 실패 뒤 이전 문서/thread가 다시 선택되는 경로
- Codex 실행과 문서 append 사이의 비원자성
- signal trap이 thread 상태를 깨뜨리지 않는 점
- `CH_RC != 0` + nonempty output을 성공 처리하는 점
- 실패 분기의 `sed`/append 오류 무시
- 락의 소유권 토큰 부재와 ABA 가능성
- subject YAML 주입, 본문 기반 턴 카운터 오염
- 코드가 uppercase slug를 허용하는 점

### 중간 — 런타임 조건에 따라 달라짐

- 상위 Bash timeout이 셸/자식 Codex에 어떤 신호 순서로 전달되는지
- Git Bash와 각 Linux 서버 파일시스템에서 noclobber의 실제 동시성 결과
- chat 문서가 Git/동기화로 머신 사이를 이동하는지, Codex thread 저장소가 머신별인지
- CRLF 변환이 실제 chat 산출물에 적용되는지
- 프로젝트가 신뢰되지 않은 심볼릭 링크를 포함할 수 있는지

### 낮음/미확정 — 추가 실측 필요

- Codex CLI 0.145.0에서 `exec resume`가 첫 턴의 `-s read-only`를 어떤 조건에서도 그대로 상속하는지
- 구성된 MCP/외부 도구가 샌드박스 밖 부작용을 낼 수 있는지
- nonzero이면서 `-o` 파일이 존재하는 실제 Codex 실패 이벤트 조합과, 그때 thread를 안전하게 재개할 수 있는지
