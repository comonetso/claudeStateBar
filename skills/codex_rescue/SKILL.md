# codex_rescue — Codex 2차 시선 자동 왕복

## 0. 의도 판정 — 다른 무엇보다 먼저 한다

발동하면 인자를 **맥락으로 읽어** 아래 6갈래 중 하나로 간다.

🔴 **키워드를 기계적으로 매칭하지 마라.** 사용자는 STT(음성 입력)로 말하므로 표현이 매번 다르다.
"리뷰시켜" · "리뷰해줘" · "바뀐 코드 봐줘" · "커밋하기 전에 훑어줘" 는 전부 같은 뜻이다.
아래 예시는 **판정 기준의 예시일 뿐 고정 목록이 아니다.**

| 사용자가 원하는 것 | 모드 | 이런 식으로 말한다 |
|---|---|---|
| 사용법 | **HELP** | `help` · `--help` · `-h` · `?` · `사용법` |
| 이미 만든 건 다시 굴리기 | **RESUME** | 인자 **전체**가 `.md` 경로 하나일 때만 |
| **직전 분석에 되묻기** | **FOLLOWUP** | "다시 물어봐" · "되물어" · "그거 반박해봐" — 또는 **내 판단으로**(§ 절차 10) |
| **짧게 주고받고 싶다** | **CHAT** (핑퐁) | "코덱스와 대화해" · "핑퐁으로 물어봐" — **명시할 때만** |
| **바뀐 코드를 봐달라** | **REVIEW** | "리뷰시켜" · "리뷰해줘" · "바뀐 거 검토해" · "커밋 전에 훑어줘" |
| **보고 고쳐달라** | **EDIT** | "검토및 수정요청해" · "분석하고 수정시켜" · "수정시켜" · "고쳐줘" · "네가 고쳐" |
| 내가 막힌 걸 봐달라 | **CONSULT** (기본) | "검토요청해" · "분석해줘" · "분석요청해" · 문제 텍스트 · **인자 없음** |

**"분석"** 은 기본적으로 CONSULT 다 (Claude 가 막힌 문제를 분석받는 것). 단 "이 코드 분석해줘"
처럼 **대상이 작업 결과물**이면 REVIEW 다. 뒤에 "수정"이 붙으면(`분석하고 수정시켜`) EDIT 다.

### 🔴 RESUME 은 파일명으로 세 갈래다 (2026-08-25, multi-turn 신설과 함께)

| 인자로 온 파일 | 무엇을 하나 |
|---|---|
| `<스탬프>_request_<슬러그>.md` | 기존 RESUME — 응답이 있으면 검토, 없으면 **재실행** |
| `<스탬프>_followup<N>_<슬러그>.md` | 그 반박서를 **`--followup` 으로 실행**한다. 이미 돌았으면(응답 문서 `turns` ≥ N) 재실행하지 말고 그 턴을 검토한다 |
| `<스탬프>_response_<슬러그>.md` | 결과를 읽고 검토 + **되물을지 판단**(§ 절차 10) |

🔴 **반박서를 요청서 경로로 실행하지 마라.** 둘은 **같은 `response_path` 를 가리키므로**
규약 검증을 전부 통과하고, Codex 가 workspace-write 로 돌면서 **1턴 원문과 `## Claude 검토` 가
담긴 응답 문서를 통째로 덮어쓴다.** N턴 대화가 한 번에 날아간다.
`send.sh` 가 양방향으로 막지만(2026-08-25 실측 확인), 애초에 그쪽으로 보내지 마라.

🔴 **CHAT 은 사용자가 명시할 때만 간다** (2026-08-22 사용자 결정). "코덱스한테 물어봐" ·
"분석해줘" 같은 기존 표현은 **전부 CONSULT 그대로**다. 판정을 흔들지 마라 — Codex 자신은
"가벼운 쪽을 기본으로 두라"고 권했지만 사용자가 반대로 정했고, 그 결정이 우선한다.

### 🔴 실행 중 끼어들기는 **항상 켜고 돈다** (2026-08-26 사용자 결정)

CONSULT 는 `CR_LIVE_STEER=1` 로 실행한다(§ 절차 8). 모드가 아니라 **켜진 채로 도는 기본 배관**이다.

**왜 기본값인가.** 이 경로가 없으면 도는 중에 말을 넣을 수 없고, `codex exec` 는 **시작한 뒤
경로를 바꿀 방법이 없다.** 그래서 "끼어들 일이 생기면 그때 켠다"가 성립하지 않는다 —
끼어들 일이 생길지는 **시작 시점에 아무도 모른다.** 켜 두지 않으면 그 순간 할 수 있는 게 없다.

| 사용자가 말한 것 | 동작 |
|---|---|
| 아무 말 없음 (기본) | **켜고 돈다** — `CR_LIVE_STEER=1` |
| "예전 방식으로" · "라이브 끄고" · "exec 로 돌려" | `CR_LIVE_STEER=0` 으로 옛 경로 |

🔴 **끼어들 계획이 없어 보여도 끄지 마라.** 켜 두는 비용은 없고, 꺼 두면 도중에 사용자가
말을 걸었을 때 **전달할 방법이 사라진다.** 판단하지 말고 켜라.

🔴 **`CR_LIVE_STEER=1` 은 CONSULT 1턴에서만 산다.** `send.sh` 는 `KIND=doc && MODE=readonly`
일 때만 분기한다. FOLLOWUP·REVIEW·EDIT·CHAT 에 붙여도 조용히 무시되므로 **그 모드에서
끼어들기를 약속하지 마라.** 각자 검증된 배관이 따로 있고, 한 번에 갈아타면 회귀 범위가
통째로 열린다.

### 판정은 두 축으로 한다

1. **대상이 무엇인가** — 작업 결과물 전체(바뀐 코드)냐, Claude 가 막힌 특정 문제냐
2. **Codex 가 고치기를 원하는가** — 의견만이냐, 직접 수정이냐

```
대상=바뀐 코드,   수정 안 함  →  REVIEW    (codex exec review, git diff 기반)
대상=막힌 문제,   수정 안 함  →  CONSULT   (요청서 기반, 가설 반박)      ← 기본
대상=막힌 문제,   수정 함      →  EDIT      (요청서 기반 + Codex 가 고침)

짧게 여러 번 주고받기  →  CHAT  (세션을 이어가며 한 줄씩)   ← 명시할 때만
```

### 애매할 때

- **REVIEW vs CONSULT** — 둘 다 읽기 전용이라 잘못 골라도 손해가 적다. 되묻지 말고
  대화 맥락으로 정한다. 방금까지 코드를 고치고 있었으면 REVIEW, 문제에 막혀 있었으면 CONSULT.
- **EDIT 이 섞였는지 애매하면 → 반드시 한 줄로 확인한다.** 코드를 실제로 고치는 동작이고
  되돌리기 비용이 크다. 맥락 판정은 오탐 여지가 있으므로 여기서만 예외적으로 되묻는다.
- **문제 설명에 그 단어가 들어간 경우** — "로그인 리뷰가 안 돼" · "수정이 안 먹혀" 처럼
  **서술형**이면 그건 모드 지시가 아니라 **문제 텍스트**다. CONSULT 로 간다.
- **"리뷰하고 고쳐줘"** — `codex exec review` 는 read-only 전용이라 Codex 가 못 고친다.
  **REVIEW 로 받아서 Claude 가 고친다.** 그게 이 스킬의 전제("작업자는 Claude")에도 맞다.
- 경로 판정이 애매하면(문제 설명에 `.md` 가 섞임) RESUME 으로 가지 않는다.

## help 출력 — HELP 모드면 이것만 낸다

```
codex_rescue — Claude가 막혔을 때 Codex에게 2차 시선을 받는 스킬 (전 과정 자동)

[무엇]  제(Claude)가 막힌 문제를 요청서 파일로 정리 → codex CLI 를 직접 호출
        → Codex가 읽고 분석해 response 파일 저장 → 제가 자동으로 받아 검토·적용
        ★ 붙여넣기도, "다 됐다"고 알려주실 것도 없습니다. 손 안 대셔도 됩니다.

[왕복]  1. Claude  → docs/codex_rescue/<스탬프>_request_<슬러그>.md  작성
        2. Claude  → send.sh 를 백그라운드로 실행 (Codex 호출)
        3. Codex   → 요청서 읽고 분석 → <스탬프>_response_<슬러그>.md 저장
                     (저장이 막혀도 -o 로 최종 메시지를 회수해 스크립트가 대신 저장)
        4. Claude  → Codex 종료 시 자동으로 깨어나 response 읽고 검토 → 적용 판단 보고

        분석이 도는 동안 다른 작업을 계속 지시하실 수 있습니다.
        ★ 도는 중에 끼어드실 수도 있습니다 — 아래 [끼어들기].

[안전]  Codex는 코드를 고치지 않습니다 (--edit 제외). 제 맥락이 끊기기 때문입니다.
        다만 저장 권한이 있으므로, 응답 파일 외에 무엇이 바뀌었는지
        send.sh 가 파일시스템으로 실측해 제게 강제 보고합니다.
        전제를 깬 변경이 있으면 제가 사용자께 보고하고 지시를 받습니다 — 임의로 되돌리지 않습니다.

[핵심]  요청서에는 **원본 자료의 실제 경로와 "직접 열어보라"는 지시**가 들어갑니다.
        제 가설은 뒤쪽에 짧게만 붙습니다 — 앞에 두면 Codex가 제 시선 안에 갇힙니다.
        ★ 귀·눈으로 확인하신 증상(끊김·깜빡임·체감 빈도)은 **제가 여쭤봅니다.**
          코드에도 로그에도 없고 형님만 아시는 정보라, 그게 빠지면 분석이 반쪽이 됩니다.

[되묻기] 한 번 받고 끝이 아닙니다. Codex 답변을 제가 검토한 뒤 **다시 되물을 수 있습니다.**
        제가 좁게 해석했으면 Codex가 그걸 교정해 줍니다 (최대 11턴).
        같은 장애를 단발로 3번 물어도 결론이 안 났는데, 형님이 직접 11턴 대화하시니
        결론이 났던 것 — 그 구조를 스킬에 넣은 것입니다.

[명령]  ★ 말씀하시면 됩니다. 정해진 키워드가 아니라 뜻으로 알아듣습니다.

  /codex_rescue                       ★ 가장 흔함. 지금 막힌 걸 제가 알아서 특정
  /codex_rescue 분석해줘 · 검토요청해   제 가설을 Codex가 반박          (코드 안 고침)
  /codex_rescue 리뷰시켜               바뀐 코드를 Codex가 리뷰        (코드 안 고침)
  /codex_rescue 리뷰시켜 인증 위주로    ↑ + 집중해서 볼 지점 지정
  /codex_rescue 분석하고 수정시켜       Codex가 직접 코드 수정          (확인 한 번 받습니다)
  /codex_rescue 코덱스와 대화해         ★ 핑퐁 — 짧게 묻고 짧게 받기   (10초 안팎)
  /codex_rescue 다시 물어봐            ★ 직전 분석에 되묻기 (제 해석이 맞는지 확인받음)
  /codex_rescue <request 경로>         응답 왔으면 검토, 안 왔으면 재실행
  /codex_rescue help                  이 도움말

[끼어들기] ★ 분석이 도는 중에 말씀하시면 그대로 Codex에게 전달됩니다.
        Codex가 하던 일을 버리지 않고, 이어가면서 반영합니다 (다시 시작하지 않습니다).

          형님: "아 참, 그 파일 서버에도 있어"
          → 제가 그대로 밀어 넣습니다 → Codex가 그 사실을 반영해 조사를 이어갑니다

        ★ 미리 켜달라고 하실 필요 없습니다. 분석해줘 / 검토요청해 는 항상 켜져 있습니다.
          (시작한 뒤엔 못 켜기 때문에, 아예 늘 켜 두는 것으로 정했습니다)
        ★ 제게 하신 말인지 Codex에게 하신 말인지 애매하면 한 줄로 여쭙니다.
        ★ 이미 끝난 분석에는 못 넣습니다 — 그건 "다시 물어봐"(되묻기)로 갑니다.
        ★ 리뷰·수정·핑퐁·되묻기에는 없습니다 (분석/검토요청 전용).

[핑퐁]  "코덱스와 대화해" 라고 하시면 짧은 왕복 모드로 갑니다. 위쪽 왕복(요청서→분석→문서)과
        달리 **이 채팅창에서 바로** 주고받습니다.

          ✳️ 클로드: <제가 던진 말>
          🔷 코덱스: <받은 답 그대로>

        두 발언이 다 보이므로 오가는 걸 보시면서 판단하실 수 있습니다.
        기록은 <프로젝트 루트>/docs/codex_rescue/<스탬프>_chat_<슬러그>.md 에 쌓입니다.
        ★ 하위 폴더에서 불러도 같은 파일에 이어집니다 (같은 슬러그면 같은 대화).
        Codex 진행 패널에는 뜨지 않습니다 (거긴 오래 도는 작업을 지켜보는 창입니다).
        ★ 질문이 무거우면 그만큼 느려집니다 — 무거운 건 "분석해줘"(정식 자문)가 맞습니다.
        ★ 파일 탐색은 기본으로 막혀 있고, 120초를 넘기면 스스로 중단합니다.
          (예전에는 16분씩 멈춘 것처럼 보이는 일이 있었습니다)

[리뷰]  "리뷰시켜" 는 git diff 를 대상으로 합니다. **git 레포에서만 됩니다.**
        - 커밋 안 된 변경이 있으면 → 그것을 리뷰
        - 작업 트리가 깨끗하면      → 기본 브랜치(main 등)와 비교
        - 특정 기준을 원하면 말씀만: "main 기준으로 리뷰해" / "이 커밋만 리뷰해"

[파일]  docs/codex_rescue/  (없으면 자동 생성. 핑퐁만 프로젝트 루트 기준이고 나머지는 현재 폴더 기준)
        260726_014119_request_mms-jar-encoding.md    ← Claude 작성 (검토·수정 요청)
        260726_014119_response_mms-jar-encoding.md   ← Codex 작성 (스탬프·슬러그 동일)
        260726_014119_review_auth-refactor.md        ← 코드 리뷰 결과 (요청서 없음)
        .log/260726_014119_events.jsonl              ← Codex 가 실제로 한 일 전체 기록

            CR_LIVE_STEER=1     끼어들기 경로 (분석/검토요청의 기본값. 0 이면 예전 방식)
```

출력 후 한 줄 덧붙인다: "바로 물어보려면 `/codex_rescue` 만 치시면 됩니다."

## 목적 (설계의 전제 — 절대 흔들지 말 것)

**모든 작업은 Claude와 사용자가 한다. Codex는 작업자가 아니라 자문역이다.**

Claude가 해결하지 못하는 문제가 가끔 생긴다. 그럴 때 **다른 시선의 분석**을 받으려고 Codex를 부른다.
따라서 이 스킬의 산출물은 "Codex가 실행할 작업지시"가 아니라 **"Codex가 반박하고 다른 각도를 제시할 분석 요청서"** 다.

이 전제에서 따라 나오는 규칙:

- **Codex는 프로덕션 코드를 수정하지 않는다.** Codex가 고치면 Claude가 모르는 변경이 생기고 맥락이 끊긴다. (`--edit` 만 예외)
- **Codex가 쓸 수 있는 곳은 두 곳이다** — 응답 문서와 `docs/codex_rescue/.scratch/`.
  🔴 **2026-08-25 개정.** 예전에는 "response 문서 하나뿐"이었다. 그런데 실측해 보니
  `workspace-write` 는 **디스크 전체 읽기와 cwd·/tmp 쓰기를 이미 허용**하고 있었다.
  즉 권한이 막은 게 아니라 **프롬프트가 스스로 족쇄를 채우고** 있었고, 그 결과 Codex 는
  파형 정렬·로그 재집계처럼 파일이 필요한 계산을 시작조차 못 하고 추론만 하다 결론에 못 갔다.
  **탐색까지 막으면 분석 자체가 안 나온다** — 이게 CONSULT 3회 실패로 확인된 것이다.
- **그 전제를 프롬프트 지시에만 맡기지 않는다.** `send.sh` 가 실행 전후를 실측 비교해
  **프로덕션 영역의** 변경을 잡아내 Claude에게 강제 보고한다. (§ 변경 감지)
  `.scratch/` 안의 것은 위반이 아니라 조사의 흔적이므로 따로 집계해 보고한다.
- **요청서에는 원본 증거를 먼저, Claude의 가설을 나중에 담는다.** 가설이 없으면 Codex 는 내가
  걸어간 길을 되밟고, 가설이 **앞에** 있으면 내 시선 안에 갇힌다.
  **가설은 검토 대상이지 분석의 출발점도 경계도 아니다** (2026-08-25 개정).
- **사용자가 감각으로 관측한 것은 코드·로그 어디에도 없다.** 그건 되물어서 받아 적는다
  (§ 절차 2 되묻기 예외).
- **응답의 최종 소비자는 Claude다.** 사용자에게 읽히는 글이 아니라, Claude가 곧바로 적용 판단할 수 있는 형태여야 한다.

## 왕복 구조 — 사람 손이 들어가지 않는다

```
Claude  ─►  docs/codex_rescue/260726_014119_request_<slug>.md   저장
Claude  ─►  Bash(run_in_background: true)
              bash ~/.claude/skills/codex_rescue/send.sh <request 경로>
Codex   ─►  요청서를 읽고 분석  ─►  260726_014119_response_<slug>.md  직접 저장
send.sh ─►  응답 회수 + 변경 실측  ─►  stdout 으로 Claude 에게 보고
Claude  ─►  ★ codex 종료 시 자동 재호출됨  →  response 읽고 검토  →  적용 판단 보고
```

**왜 백그라운드인가** — Claude Code 의 `run_in_background` 는 명령이 끝나면 **Claude를 자동으로 다시 깨우고 stdout을 넘긴다.** 그래서 hook을 등록하지 않아도 도착을 즉시 인지한다. 동기 호출은 Bash 타임아웃(최대 10분)에 걸릴 수 있고 대기 중 다른 작업을 못 한다. 백그라운드면 Codex가 분석하는 동안 사용자가 다른 일을 계속 지시할 수 있다.

**왜 파일로 주나** — 긴 요청서를 인자로 넘기면 따옴표·개행이 깨진다. 경로만 넘기고 Codex가 직접 읽는다. 그리고 요청·응답이 프로젝트에 기록으로 남아 git으로 추적된다.

**쓰기 실패로 왕복이 끊기지 않는다** — `send.sh` 는 `codex exec -o <파일>`(`--output-last-message`)로 Codex의 최종 메시지를 항상 파일로 받아둔다. Codex가 지정 경로에 저장하지 못했으면 스크립트가 그 메시지를 규약 형식으로 감싸 `response_path` 에 저장하고 `author: codex-via-stdout` 으로 표시한다. **사용자가 답변을 옮겨 붙일 일은 없다.**

## 변경 감지 — workspace-write 의 구멍을 막는다

Codex 는 `-s workspace-write` 로 실행된다(응답 파일을 직접 저장하려면 필요하다). 그러면 **워크스페이스 안의 다른 파일도 쓸 수 있다.** "Codex는 코드를 고치지 않는다"는 전제가 프롬프트 준수에만 의존하게 되므로, `send.sh` 가 파일시스템으로 실측한다.

- 실행 직전 **마커 파일**(시간 기준점)과 **전체 파일 경로 목록**을 남긴다
- 실행 후 마커보다 새로운 mtime = 생성·수정, 경로 목록 차집합 = 삭제
- 정상 산출물(`response_path`, `.log/`, `.scratch/`)을 뺀 나머지가 **프로덕션 영역의 변경**이다
- 있으면 stdout에 🔴 로 보고된다. Claude는 그것을 **반드시 사용자에게 보고**한다
- 🔴 **임의로 되돌리지 않는다.** 되돌릴지 살릴지는 사용자 판단이다
- `.log/<스탬프>_events.jsonl` 에 Codex가 실행한 모든 이벤트가 남는다. 무엇을 했는지 따질 때 이걸 읽는다.
  **이 파일은 실행 중에도 실시간으로 쌓이므로**, 도는 동안 진행 상황을 물어보면 이걸 읽어 답할 수 있다
  (`_status.json` 의 `state` 가 현재 단계 — `running` / `finalizing` / `done` / `failed` / `interrupted`).
  claudeStateBar 확장(v1.9.0+)이 이 두 파일로 진행 패널을 그린다
  (포맷이 바뀌면 깨지므로 스크립트는 파싱하지 않고 보존만 한다)

성능 때문에 `.git`·`node_modules`·`build`·`.gradle`·`.dart_tool`·`.venv`·`.next`·`__pycache__` 는 스캔에서 제외한다. **그 안의 변경은 못 잡는다** — 의도된 절충이다.

**`docs/codex_rescue/.scratch/` 는 스캔은 하되 경보에서만 뺀다** (2026-08-25). Codex 의 작업대이므로
거기 생긴 파일은 위반이 아니라 조사의 흔적이다. prune 하지 않은 것은 의도적이다 — 그러면 무엇을
계산했는지 보고에서 사라지고, 그 흔적이 곧 조사 재현의 근거이기 때문이다. 몇 건이 생겼는지는
`🧪` 줄로 따로 보고된다.

🔴 제외 규칙은 **앵커드 접두**(`^docs/codex_rescue/\.scratch/`)로 되어 있다. `grep -v scratch`
같은 부분 일치로 바꾸면 `src/scratchpad.js` 가 통째로 묻힌다 — **제외 규칙이 넓어지는 순간
그게 곧 감시 우회 통로가 된다.**

## 이중 위임 — 하지 않는다

`remote_req` 로 서버 Claude 를 깨워서 `codex_rescue` 를 시키지 마라.

대신 서버에 **사실을 묻고**, 받은 답을 재료로 **로컬에서** Codex 에 묻는다.

> 서버 Claude 는 `remote_req` 헤더로 "물어본 것만 답한다·고치지 않는다"가 강제된 비대화형
> 세션이라 스스로 다른 스킬을 발동할 이유가 없다. 로컬 Claude 가 **명시적으로**
> "코덱스한테 물어봐"를 보내야 성립하는데 그럴 이유가 없다.
>
> **사용자가 서버에 직접 접속해 `codex_rescue` 를 쓰는 것은 금지가 아니다** — 그래서 4대에 배포했다.
> 금지 대상은 "자동 연쇄"뿐이다.

## 언제 어느 스킬을 쓰는가 (2026-08-17 추가)

`remote_req` 와 `codex_rescue` 는 **"요청"·"검토" 라는 말이 겹치는데 생명주기가 정반대**다.
Codex 가 지적한 혼동 지점이라 표로 고정한다.

| 하려는 것 | 쓸 것 | 상대를 깨우나 |
|---|---|---|
| 서버/앱 Claude 에게 **사실을 묻기** | `remote_req` QUERY | 깨운다 (답이 온다) |
| 상대 팀에 **수정 요청서 남기기** | `remote_req` REQUEST | **안 깨운다** (문서만 떨군다) |
| 내가 한 변경을 **알리고 영향만 받기** | `remote_req` NOTICE | 깨운다 |
| **내가 바꾼 코드**를 검토받기 | `codex_rescue` REVIEW | Codex 를 깨운다 |
| **내가 막힌 문제**의 가설을 반박받기 | `codex_rescue` CONSULT | Codex 를 깨운다 |
| Codex 에게 **직접 고치게** 하기 | `codex_rescue` EDIT | 깨운다 + **게이트** |

핵심 구분: **`remote_req` = 공간 축**(멀리 있는 Claude) · **`codex_rescue` = 관점 축**(다른 모델).

## CHAT 절차 — "코덱스와 대화해" 로 발동 (2026-08-22 신설)

사용자와 Claude 가 대화하는 중에 **다른 시선이 한 번 필요할 때** 쓴다.
"코덱스, 너는 어떻게 생각하니?" 를 그 자리에서 던지고 그 자리에서 받는다.

🔴 **사용자가 명시했을 때만 온다.** "분석해줘"·"코덱스한테 물어봐" 는 CONSULT 그대로다.

1. **슬러그를 정한다** — 영문 kebab-case 2~4단어. **파일 이름과 락의 단위**다.
   🔴 **슬러그는 대화 식별자가 아니다** (2026-08-22 개정). 식별자는 `send.sh` 가 발급하는
   **대화키**(`ymd_His`)이고, 슬러그는 그 파일 이름에 붙는 주제 이름일 뿐이다.
   같은 슬러그를 다시 써도 **새 스킬 호출이면 새 대화**다. 주제가 바뀌면 슬러그를 바꾼다.

2. **질문을 짧게 쓰고, 볼 것을 지목한다.** 🔴 **이게 이 모드의 전부다.**

   실측(2026-08-25, 320파일 실제 레포)이 예전 전제를 뒤집었다. 느려지는 원인은
   **"탐색을 켜서"가 아니라 "대상을 지목하지 않아서"** 다.

   | 상황 | 시간 | Codex 가 돌린 명령 |
   |---|---|---|
   | 탐색 개방 + 가벼운 질문 | 7초 | 0회 |
   | 탐색 개방 + **파일명을 지목한** 코드 질문 | 25초 | 1회 |
   | **`--look` 인라인 13KB** + 같은 질문 | **8초** | 0회 |
   | `--look` 인라인 56KB | 12초 | 0회 |
   | 탐색 개방 + **대상 없는** 넓은 설계 질문 | **240초 초과** | **105회** |

   - **코드를 봐야 하는 질문이면 `--look <경로>` 로 지목한다.** 스크립트가 그 파일을
     프롬프트에 **직접 실어 보낸다.** 그래서 Codex 는 파일을 찾을 필요가 없고, 탐색 차단이
     그대로 살아 있는 채로 근거 있는 답이 나온다. 실측상 **가장 빠르고 답도 가장 정확했다**
     (탐색으로 찾게 한 쪽보다 3배 빠르고 함수명까지 정확히 집었다).
     - 일부만 보여주려면 `--look <경로>:<시작>-<끝>`
     - 여러 번 쓸 수 있다. 디렉토리는 못 준다 — **볼 파일을 내가 정하는 것**이 이 옵션의 요점이다
     - 총 64KB 를 넘으면 거부된다(`CR_CHAT_LOOK_MAX`). 그보다 크면 핑퐁의 크기가 아니다
   - 한 번에 **하나만** 묻는다. 부족하면 한 줄 더 던지면 된다 — 그게 핑퐁이다.
   - **60초를 넘기면 스크립트가 중단한다**(`CR_CHAT_LIMIT`). 위 표에서 60초에 걸리는 것은
     맨 아랫줄 하나뿐이다 — 즉 **지목이 빠졌다는 신호**다. 쪼개거나 `--look` 을 붙여라.
   - 답 길이도 지정한다 — "3줄 이내로" · "한 줄로 답하고 이유 한 줄".
   - 어디를 볼지 **Claude 도 모르는** 질문이면 애초에 CHAT 이 아니라 CONSULT 다.

   #### 탐색 정책 세 단계

   | | Codex 가 볼 수 있는 것 | 상한 |
   |---|---|---|
   | 기본(옵션 없음) | 이 대화에 주어진 것만 | 60초 |
   | **`--look <경로>`** | 대화 + **Claude 가 실어 준 자료** (탐색은 여전히 차단) | 60초 |
   | `--explore` | Codex 가 스스로 트리를 훑는다 | **`CR_CHAT_LIMIT` 명시 필수** |

   - `--look` 과 `--explore` 는 **함께 쓸 수 있다.** 그러면 "이걸 먼저 보고, 부족하면 찾아봐라"가
     된다. 지목이 시작점을 좁히므로 `--explore` 단독보다 탐색량이 줄어든다.
   - 🔴 **`--explore` 만 쓰면 스크립트가 거부한다.** `CR_CHAT_LIMIT` 을 함께 대야 한다.
     60초로는 탐색이 거의 확실히 잘리고, 잘리면 **스레드까지 폐기**되어 턴이 통째로 날아간다.
     조용한 실패를 만들지 않으려고 두 번의 의식적 선택을 요구한다(EDIT 게이트와 같은 구조).
   - **`--look` 을 먼저 의심해라.** `--explore` 가 필요한 경우는 실제로 드물다.

3. **동기로 실행한다.** 🔴 **`run_in_background` 를 쓰지 마라 — 다른 모드와 정반대다.**
   답을 받아 곧바로 채팅에 옮기는 것이 이 모드의 목적이므로, 백그라운드로 던지면 의미가 사라진다.

   🔴 **매 턴 `--start` 와 `--resume-stamp` 중 하나를 반드시 붙인다.** 빠뜨리면 스크립트가
   거부한다 — 이게 대화를 **스킬 호출 단위로** 나누는 유일한 신호다 (2026-08-22 신설).

   ```
   # 이번 스킬 호출의 첫 턴 — 항상 새 문서. 대화키는 send.sh 가 발급한다
   Bash(timeout: 180000):
     bash ~/.claude/skills/codex_rescue/send.sh --chat --start --slug <슬러그> [--subject "<한 줄>"] "<질문>"

   # 같은 호출의 다음 턴 — 직전 stdout 의 `대화키:` 값을 그대로 넘긴다
   Bash(timeout: 180000):
     bash ~/.claude/skills/codex_rescue/send.sh --chat --resume-stamp <대화키> --slug <슬러그> "<질문>"

   # ★ 코드를 봐야 하는 질문 — 볼 것을 지목한다 (가장 흔한 형태가 될 것이다)
   Bash(timeout: 180000):
     bash ~/.claude/skills/codex_rescue/send.sh --chat --start --slug <슬러그> \
       --look src/main.js --look src/db.js:40-120 "<질문>"
   ```

   - 🔴 **새 `/codex_rescue` 호출이면 첫 턴은 무조건 `--start`다.** 앞선 대화의 대화키가 이 창에
     보이더라도 재사용하지 마라. **이 의미 판단만은 스크립트가 검증할 수 없다** — 나머지 오류
     (누락·오타·없는 대상·닫힌 대상·다른 머신)는 전부 codex 를 부르기 전에 막힌다.
   - `--subject` 는 문서 제목용이며 **`--start` 에서만** 쓴다. 진행 패널에 안 뜨므로 카드 제목이 아니다.
   - 대화를 닫기만 하려면 `--close-stamp <대화키>` (codex 를 부르지 않는다). `--new` 는 없어졌다.

4. **양쪽을 다 채팅에 낸다.** 사용자가 왔다 갔다를 봐야 판단할 수 있다 — 그게 이 모드의 존재 이유다.

   ```
   ✳️ **클로드:** <내가 던진 말>          ← 실행 **전에** 낸다
   🔷 **코덱스:** <받은 답 그대로>         ← 실행 후
   ```

   🔴 **이 두 이모지를 바꾸지 마라** (2026-08-22 사용자 지정). 상태바의 프로바이더 아이콘과
   색을 맞춘 것이다 — Claude 는 주황, Codex 는 푸른색. 목록에서 누가 말했는지 색으로 먼저 읽힌다.
   상태바 쪽 진짜 아이콘(`ccb-claude`·`ccb-codex`)은 `provider-icons.woff` 의 Private Use Area
   글리프라 **채팅 마크다운에서는 두부로 깨진다.** codicon 문법(`$(...)`)도 안 먹는다.

   🔴 **Codex 답변을 요약하거나 다듬지 마라.** 원문 그대로 옮긴다. 사용자가 보는 것은 Codex 의
   말이지 Claude 가 이해한 Codex 가 아니다. 내 판단은 그 아래에 **따로** 붙인다.

5. **내 판단을 덧붙인다.** 동의든 반박이든 한두 줄. 이게 있어야 핑퐁이지, 받아쓰기가 아니다.

6. **대화 문서 링크는 핑퐁이 끝났을 때 한 번만 낸다** (2026-08-22 사용자 지시).

   🔴 **턴마다 내지 마라.** 한 주제로 여러 턴을 연달아 돌릴 때 중간에 링크가 끼면 대화 흐름을
   끊는다. 그 주제를 **마무리하고 사용자에게 공을 넘기는 시점**에 마지막 한 줄로 낸다.

   ```
   → 기록: [260822_141436_chat_joke-pingpong.md](docs/codex_rescue/260822_141436_chat_joke-pingpong.md) · 2턴
   ```

   왜 필요한가 — 채팅창은 턴이 다른 말들 사이에 흩어지지만 문서는 대화 전체가 한 화면에 있다.
   **맥락을 한꺼번에 보려고** 여는 것이다. 그래서 중간이 아니라 다 끝난 뒤에 줘야 쓸모가 있다.

   - 판정 기준: 이번 답변에서 더 이상 Codex 에게 던지지 않고 끝낼 때. 나중에 사용자가 "한 번 더
     물어봐" 하면 그건 새로운 마무리 시점이고, 그때 다시 낸다.
   - 경로는 `send.sh` stdout 의 `기록  :` 줄에 상대경로로 그대로 나온다. **추측하지 말고 그 값을 쓴다**
     — 스탬프는 `send.sh` 가 만들고, 이어받기냐 새 스레드냐에 따라 파일이 달라진다.
   - 마크다운 링크로 내면 VS Code 에서 클릭 한 번에 열린다. **패널에 띄우자는 게 아니다** — 링크만.

### CHAT 이 다른 모드와 다른 점 — 실수하기 쉬운 지점

| | CONSULT·REVIEW·EDIT | CHAT |
|---|---|---|
| 호출 | `run_in_background: true` | **동기** |
| 요청서 | CONSULT·EDIT 은 필요 | 불필요 — 인자로 바로 던진다 |
| 진행 패널 | 카드로 뜬다 | **안 뜬다** (`.log/` 에 이벤트를 안 쓴다) |
| 권한 | workspace-write | **read-only 고정** (아래 🔴 참조) |
| 변경 감지 | 실측 스캔 | **없음** — 쓰기 권한이 없어 감지할 변경이 안 생긴다 |
| 사용자가 읽는 곳 | 문서 / 패널 | **채팅창** |

> ### 🔴 `resume` 은 read-only 를 상속하지 않는다 (2026-08-22 실측)
>
> `codex exec resume` 에는 `-s` 플래그가 **없다.** 그래서 첫 턴의 `-s read-only` 가 이어질 거라
> 가정했는데, **틀렸다.** resume 턴에 "파일을 써봐라"를 시켰더니 **실제로 파일이 만들어졌다.**
>
> 즉 2턴부터 Codex 에게 쓰기 권한이 열려 있었고, CHAT 은 변경 감지를 빼 놨으므로 **아무도 그걸
> 못 잡는 상태**였다. `-c sandbox_mode="read-only"` 로 강제해 막았고 재실측으로 차단을 확인했다.
>
> 🔴 **`send.sh` 의 resume 호출에서 이 오버라이드를 빼지 마라.** 빼는 순간 감시 없는 쓰기가 열린다.

- **실패하면 스레드가 폐기된다.** Codex 세션에는 답 없는 턴이 남는데 문서에는 안 남아, 그대로
  재개하면 양쪽 맥락이 어긋난다(Codex 가 이 설계를 검토하며 지적한 것). 문서에 `⚠️ 스레드 끊김`
  이 남고 다음 턴은 새 대화로 시작한다. **끊긴 걸 억지로 잇지 마라.**
  실패 판정은 **종료 코드와 응답 유무를 함께** 본다 — 출력이 일부 있어도 exit 이 0 이 아니면 실패다.
- **강제 종료된 실행은 다음 실행이 복구한다.** codex 호출과 문서 기록 사이에서 죽으면(SIGKILL·
  타임아웃) 세션만 전진하고 문서는 옛 thread_id 를 그대로 갖는다. `.log/.chat_<슬러그>.inflight`
  마커가 그 구간을 표시하고, 다음 실행이 마커를 발견하면 스레드를 폐기한다.
  **마커를 손으로 지우지 마라** — 지우면 어긋난 세션을 그대로 재개한다.
  마커에는 복구용 필드(`started`·`pid`·`thread`) 외에 **이번에 던진 질문 원문과 `stamp`·`slug`·
  `subject`** 도 담긴다(`--- msg ---` 뒤가 원문). 대화 문서는 답이 온 뒤에야 턴을 적으므로,
  그 7~13초 동안 claudeStateBar 의 Codex 채팅 패널이 이 마커를 읽어 **"답을 기다리는 중" 턴을
  먼저 그린다**(2026-08-22). 문서를 미리 건드리지 않는 쪽을 고른 이유는 실패했을 때 반쪽짜리
  턴이 기록에 남지 않게 하기 위해서다 — **문서는 확정된 것만 담는다.**
- **다른 머신에서 시작된 대화는 안 이어진다.** 대화 문서는 git 으로 오가지만 Codex 세션 저장소는
  머신마다 따로다. frontmatter 의 `origin` 이 다르면 이어받기를 포기하고 새 대화로 시작한다.
- **`--close-stamp` 는 대화를 닫기만 한다** (codex 를 부르지 않는다). 대상 문서의 `thread_id` 를
  비우고 `⏹ 새 대화로 전환` 을 남긴다. 옛 `--new` 를 대신하는데, `--new` 는 "새로 시작"과
  "옛 문서 닫기"를 한 동작에 묶고 **닫을 대상을 glob 으로 추측**해서 잘못 고른 문서를 영구히
  닫을 수 있었다. 이제 닫을 대상을 명시해야 한다.
- **세션 락이 걸린다.** 같은 슬러그에 두 턴을 동시에 던지면 거부된다 — 응답 순서가 뒤섞이기 때문이다.
  락에는 nonce·pid·host·시각이 적히고, **자기 nonce 일 때만** 푼다(남의 락을 지우지 않게).
- ⚠️ **Bash 타임아웃(3분)에 걸려도 실행은 이미 끝나 있을 수 있다.** 실측(2026-08-22): 답이
  도착하고 대화 문서까지 기록된 직후에 잘렸다. **타임아웃 = 실패로 단정하지 말고 대화 문서부터
  확인해라.** 락은 그 경우에도 정상적으로 풀렸다.

## REVIEW 절차 — "리뷰시켜" 로 발동

   🔴 **`10` 을 "안 시작했다"로 읽지 마라.** `Conn.request()` 는 `turn/start` 프레임을 **보낸 뒤**
   응답을 기다리므로, 응답 타임아웃·연결 유실·turnId 없는 응답도 전부 10 이 된다
   (`appserver.mjs:342-365` · `live-consult.mjs:791-804`). **서버가 이미 턴을 시작했는데 응답만
   잃은 경우를 코드가 구분하지 못한다.** 폴백하면 같은 조사를 두 번 시키고 한도를 두 배로 태운다.

   🔴 **"실패했으니 일단 다시"를 하지 마라.** `11` 외에는 전부 `.log/<스탬프>_appserver.jsonl` 과
   `_stderr.log` 를 읽어 원인을 사용자에게 보고하고 **판단을 받는다.** 재실행은 사용자 몫이다.

### 🔴 8-1. 실행 중 끼어들기 — 사용자 말을 그대로 중계한다 (2026-08-26 신설)

절차 8 이 돌고 있는 **그 사이**의 이야기다. 돌고 있는 턴에 말을 얹으면 Codex 가 **하던 작업을
버리지 않고** 다음 모델 경계에서 반영한다(2026-08-25 실측 3회, `turns` 는 늘지 않는다).
`codex exec` 로는 원리적으로 불가능한 동작이라, 이 절차는 `CR_LIVE_STEER=1` 로 돌 때만 성립한다.

#### 던지는 법 — 본문은 반드시 파일로 넘긴다

```
1. Write:  docs/codex_rescue/.log/<스탬프>_steer<N>.txt      ← 사용자 말을 그대로
2. Bash:
     node ~/.claude/skills/codex_rescue/scripts/live-consult.mjs steer \
       --stamp <스탬프> \
       --input-file docs/codex_rescue/.log/<스탬프>_steer<N>.txt \
       --source user-via-claude
```

🔴 **긴 한글을 argv 로 넘기지 마라.** Windows CreateProcess 는 32,767자 제한이 있고 한글은
UTF-8 3바이트라 더 빨리 걸린다(실측: 32,000B 성공 / 32,700B 실패). `--input-file` 이 있는
이유가 그것이다. 짧아 보여도 파일로 넘겨라 — 길이를 재는 순간 판단이 하나 더 늘어난다.
(`--input-file -` 로 stdin 도 받는다)

**`<스탬프>` 는 요청서 파일명의 그 값이다.** 절차 7에서 내가 정한 값이므로 이미 알고 있다.
**추측하거나 새로 만들지 마라.** `send.sh` stderr 의 `대화키:` 줄과 같은 값이다.

#### 언제 던지나 — 사용자가 말했을 때만이다 (2026-08-26 사용자 결정)

| 상황 | 동작 |
|---|---|
| 실행 중 사용자가 **Codex 에게 갈 말**을 했다 (새 사실 · 조사 방향 · 놓친 원본) | **그대로 중계한다.** 던진 뒤 한 줄로 밝힌다 |
| 사용자 말이 **나(Claude)에게 한 말**로 읽힌다 | 던지지 않는다. 평소대로 답한다 |
| **둘 중 어느 쪽인지 애매하다** | **한 줄로 묻는다.** "이거 Codex 에 넣을까요?" |
| 그 외 전부 | 던지지 않는다 |

🔴 **Claude 가 스스로 판단해서 던지지 마라.** 중계기에 `wait`(고신호 감시) 서브커맨드가 있지만
**쓰지 않기로 했다**(2026-08-26 사용자 결정). Codex 가 헛다리를 짚는 것처럼 보여도 내 오판일
수 있고, 그 오판이 진행 중인 조사를 흔든다. 이상하면 **사용자에게 알리고 판단을 받는다.**

🔴 **사용자 말을 요약·각색·번역하지 마라. 그대로 넘긴다.** 내 시선을 거치는 순간 이 스킬의
존재 이유가 사라진다 — 요청서에 원본을 옮겨 담지 않는 것(절차 6)과 같은 논리다. 맥락이
필요하면 사용자 말 **아래에** 덧붙이되, 사용자 말 자체는 원문 그대로 맨 위에 둔다.

#### 결과 판정 — 종료 코드로 본다 (2026-08-26 Codex 코드 대조로 확정)

| 코드 | 뜻 | 사용자에게 어떻게 말하나 |
|---|---|---|
| **0** | 전달됐다 — outcome 이 `delivered` (같은 turnId 를 strict 비교) | "전달했습니다" |
| **30** | enqueue 뒤 `rejected` 로 기록됐다 | 사유를 그대로 전한다. **단 "서버가 거부했다"고 단정하지 마라** (아래) |
| **31** | enqueue **전** steerability 검사 실패 — 그 실행이 없거나 개입 불가 상태 | 이미 끝났을 수 있다. `status` 로 확인하고 알린다 |
| **32** | enqueue 했지만 전달 확인 불명 (`unknown` · phase 종료 · deadline 만료) | 🔴 **"전달됐다"고 말하지 마라.** "전달 여부가 불명확하다"고 한다 |
| **1 · 2 · 11** | 예상 밖 오류 / 인자·입력 오류 / lib 로드 실패 | **내 호출이 틀렸을 가능성부터 본다** |

🔴 **`30` 을 "서버가 거부했다"로 옮기지 마라.** 30 에는 서버의 명시적 거부 외에 **steer 채널
없음 · turnId 불일치 · 턴 종료 뒤 남은 큐 · RPC 응답 타임아웃**이 함께 들어간다
(`live-consult.mjs:851-951` · `897-905`). 요청 프레임은 이미 나간 뒤라 **서버가 받았는데 응답만
늦은 경우도 30 이다.** 사유 문자열을 그대로 전하고, 해석은 붙이지 마라.

🔴 **"큐에 넣었다"를 "전달됐다"로 말하지 마라.** 중계기는 같은 turnId 응답을 받은 뒤에만
전달로 친다. 32번은 불명이고, 불명을 성공으로 보고하면 사용자가 반영됐다고 믿고 다음 판단을 한다.

⚠️ **`exit 0` 이 곧 전달은 아니다.** `--help` · `--version` · `--dry-run` 도 0 이다
(`live-consult.mjs:1431-1435`). 전달 판정은 **`전달됨 · seq=N · turnId=…` 출력과 함께** 본다.

⚠️ **리뷰·컴팩션 턴은 원리적으로 steer 불가다** (`NonSteerableTurnKind = ["review","compact"]`).
REVIEW 모드에 이 경로가 없는 이유이기도 하다.

⚠️ **끝난 턴에는 못 넣는다.** 다만 **끝난 턴이 항상 31 인 것은 아니다.** 초기 검사 시점에 이미
끝나 있었으면 31, 검사를 통과한 뒤 경합으로 끝났으면 **30 또는 32** 로 나온다
(`-32600 no active turn to steer` 는 enqueue 뒤 경로라 **30** 이다). 어느 쪽이든 그 턴에는
못 넣은 것이니 되묻기(§ 절차 11)로 간다.

9. **자동 재호출 → 검토** — Codex 가 끝나면 Claude 가 **자동으로 깨어나** `send.sh` 의 stdout 을 받는다. 사용자가 알려줄 필요가 없다. 받으면:

   1. 보고에 🔴 **응답 파일 외 변경**이 있으면 **그것을 가장 먼저 사용자에게 보고한다.** 스킬 전제가 깨진 것이므로 검토보다 우선한다. **임의로 되돌리지 마라** — 되돌릴지는 사용자 판단이다.
      (`🧪 Codex 작업 폴더에 N건` 은 **정상이다.** `.scratch/` 안의 조사 흔적이지 위반이 아니다)
   2. `response_path` 를 Read 한다. **Codex 원문을 고치지 마라.** 파일 끝에 `## Claude 검토` 섹션을 덧붙인다.
   3. ⬛ **완료 게이트를 통과해야 완료다** (바로 아래). 통과 못 하면 완료라고 보고하지 마라.
   4. 검토 결과(채택 / 보류 / 기각 + 각각의 이유, 적용 계획)를 보고하고 적용 여부 판단을 받는다.
   5. 응답 파일이 없다고 나오면 `.log/<스탬프>_events.jsonl` 과 `_stderr.log` 를 읽어 원인을 사용자에게 보고한다.

### ⬛ 완료 게이트 — 자기신고가 아니라 실행 기록으로 판정한다 (2026-08-25 신설)

**응답 문서의 "직접 열었다"를 믿지 마라.** `.log/<스탬프>_events.jsonl` 에 Codex 가 실행한 모든
명령이 남는다. 그걸로 실측한다.

```bash
L=docs/codex_rescue/.log/<스탬프>_events.jsonl
# ① 명령을 몇 개나 실행했나
grep '"type":"item.started"' "$L" | grep -c '"command_execution"'
# ② 실행한 명령 전문 목록
grep '"type":"item.started"' "$L" | grep '"command_execution"' \
  | sed -E 's/.*"command":"//; s/","aggregated_output.*//'
# ③ 요청서 원본 표의 항목이 실제로 명령에 등장했나 — 항목마다 반복
grep '"type":"item.started"' "$L" | grep -c '<파일명 또는 사례ID>'
```

🔴 **반드시 `item.started` 줄로 한정해라.** 파일 전체를 grep 하면 요청서를 읽은 명령의
`aggregated_output` 에 **요청서 본문이 통째로** 들어 있어 전부 걸린다(위양성).
🔴 **경로 전체로 grep 하지 마라.** 명령문 안의 경로 구분자는 JSON 이스케이프돼 있다
(Windows 는 `\\\\`). **파일명이나 사례 ID 같은 구분 토큰**으로만 찾는다. (2026-08-25 실측 확인)

🔴 **명령문에 파일명이 보이는 것만으로 "읽었다"고 판정하지 마라** (2026-08-25 Codex 지적).
`echo <파일명>` 도 통과하고, 변수·glob 으로 열면 안 잡힌다. **두 가지를 함께** 본다.

1. **그 명령이 실제로 끝났나** — `item.completed` 에 `exit_code: 0`
2. **응답에 그 원본에서만 나올 수 있는 값이 있나** — 수치·대조 결과·`.scratch/` 산출물 경로

| 실측 결과 | 판정 |
|---|---|
| `command_execution` 0건 | ❌ **아무것도 안 열고 추론만 했다** |
| 원본 표의 항목이 명령에 **하나도** 안 나옴 | ❌ **원본 미개봉** |
| `ls`·`find` 만 있고 **실제 읽기·계산 명령**(`cat`·`python`·`node`·`ffprobe` 등)이 없음 | ❌ **목록만 봤다** |
| 명령은 있는데 **응답에 그 원본에서 나온 값이 없음** | ❌ **열었다고만 하고 안 썼다** |
| 답변의 "접근 불가 자료" 칸에 요청서 원본 표의 항목이 적힘 | ❌ **탈출구 남용** |
| 위 전부 통과 | ✅ 원본은 봤다 → 아래 종료 판정으로 |

🔴 **"추가 계측이 필요하다"만 담긴 응답을 사용자에게 그대로 전달하지 마라.** 지금 열 수 있는
원본이 남아 있으면 **Claude 가 직접 연다.** 그것이 이 게이트의 목적이다.

## RESUME 모드 — 인자가 request 파일 경로일 때

요청서를 **새로 쓰지 않는다.** 이미 만든 건을 다시 굴리는 모드다.

1. 그 경로를 Read 한다. 없으면 `docs/codex_rescue/` 를 훑어 비슷한 이름을 제시하고 멈춘다.
2. frontmatter 의 `response_path` 를 읽는다.
3. **응답 파일이 이미 있으면** — Read 해서 검토하고 적용 판단을 보고한다. (§ 절차 9 와 동일)
4. **아직 없으면** — 그 건을 다시 실행한다 (§ 절차 8 과 동일). 실행 전 `.log/<스탬프>_stderr.log` 가 있으면 먼저 읽어 **지난 실패 원인을 파악하고 같은 실패를 반복하지 않는다.**
5. 요청서 내용을 채팅에 다시 뿌리지 않는다 — 파일이 정본이다.

## 이 요청의 성격 — 독립 조사 위임
나(Claude)는 이 문제에서 막혔다. 너에게 **이 사건을 직접 조사해 달라**고 부탁한다.

이 문서는 사건 개요서지 정답의 범위가 아니다. 내가 정리한 자료 안에서만 답을 찾을 이유가 없다 —
**나는 이미 그 안에서 답을 못 찾았다.** 같은 자료를 같은 방식으로 읽으면 같은 결론에 도달한다.
아래에 원본 경로를 적어 두었으니 **직접 열어서 네 방법으로 다시 봐라.**

- **원본이 내 요약과 충돌하면 원본이 이긴다.**
- 내 가설은 검토 대상일 뿐 **분석의 출발점도 경계도 아니다.**
- 필요한 계산·정렬·파싱은 직접 실행해라. 산출물은 `docs/codex_rescue/.scratch/` 에
  마음껏 만들어라 — 개수·크기 제한 없고 지우지 않아도 된다.

## 사용자가 직접 관측한 것     ← 코드·로그·DB 어디에도 없다. 가장 강한 증거다
아래는 **사용자가 자기 감각으로 확인해 말한 것**을 원문 그대로 옮긴 것이다.
내 해석도 가설도 섞이지 않았다. **이 관측은 계측치보다 먼저다.**

> "<사용자 발화 원문 그대로>"
> "<사용자 발화 원문 그대로>"

- 관측 조건: <언제 / 어느 기기 / 어느 경로로 확인했는지>
- 🔴 **사용자가 이미 해봤고 기각한 방향:** <있으면 적는다. **다시 제안하지 마라**>
- 아직 확인하지 못한 것: <미확인 항목. 추측으로 메우지 마라>

(관측 증상이 없는 건 — 빌드 실패·컴파일 에러 등 — 은 이 섹션과 아래 둘을 `해당 없음` 한 줄로 접는다)

## 계측치와의 대조     ← 어긋나면 그것이 단서다
- 계측 결과: <지표 · 값 · 산출 방법>
- 사용자 체감: <위 관측의 빈도·강도>
- 🔴 **둘이 어긋나면 사용자의 관측을 먼저 기각하지 마라.** 계측 범위·제외 조건·집계 모수·
  샘플링 지점의 **사각지대**를 먼저 의심해라. "계측에 적게 잡혔다"는 "실제로 적다"가 아니다.

## 대표 사례와 대조군
- **문제 사례(golden case):** <ID / 시각 / 식별자>  ← 이 한 건을 끝까지 파고들어라
- **정상 대조군:** <ID / 시각 / 식별자>  ← 같은 방법으로 비교해라
- 요약 통계 전체를 훑는 것보다 **이 두 건을 원본으로 대조하는 쪽이 낫다.**

## 지금 바로 열 수 있는 원본     ← 요구하지 말고 열어라
아래는 **지금 이 순간 실재하는 파일·테이블이다.** "요청하면 줄 수 있는 것"이 아니라
**이미 네 손이 닿는 곳에 있는 것**이다. 읽기 전용으로 직접 열어서 조사해라.

| 무엇 | 절대경로 / 접근 명령 | 왜 중요한가 |
|---|---|---|
| <원본> | `<절대경로>` | <...> |
| <로그> | `<절대경로>` | <타임스탬프 대조> |
| <DB>  | `<실행 가능한 조회 명령 그대로>` | <상태 확인> |

- 계산·정렬·재집계·파형 비교가 필요하면 **직접 해라.** inline python/node/셸로 충분하다.
  임시 파일은 `docs/codex_rescue/.scratch/` 안에서 자유롭게 만들어라.
- 🔴 **위 표에 있는 것을 "제공해 달라"고 답변에 적지 마라.** 그건 이미 열 수 있다.
- 🔴 **`ls`·`find` 로 목록만 확인한 것은 연 것이 아니다.** 내용을 읽고 계산까지 해야 연 것이다.

## 먼저 할 것 — 추론보다 관측이 앞선다
1. 위 표의 원본을 **실제로 열어라.** 무엇을 어떤 명령으로 열었는지 답변 1번에 적어라.
2. 대표 사례와 정상 대조군을 **같은 방법으로** 대조해라.
3. 요약 지표와 원본이 어긋나면 **원본을 믿고**, 지표가 왜 못 잡았는지 밝혀라.
4. 🔴 **`사용자가 직접 관측한 것` 이 설명되기 전에는 수정안을 쓰지 마라.**
   설명되지 않은 채 "추가 계측을 넣자"로 끝내는 답변은 이 요청의 실패다.

## 환경
- 언어/프레임워크/버전, 기기, 빌드·툴 체인 (구체적으로)

## 문제 — 증상
- 무엇이 어떻게 어긋나는지. "안 된다"가 아니라 관측된 차이로.

## 현재 코드
- 문제 지점의 실제 코드 인용(핵심 함수·호출부·시그니처) + **원본 파일 경로와 라인.**
  인용은 시작점이고 원본이 정본이다. 인용 밖이 궁금하면 파일을 열어라.

## 내(Claude)가 세운 가설     ← 증거가 아니다. 검토 대상일 뿐이다
- 나는 원인을 <X>라고 본다. 근거: <...>. 그래서 <Y>를 시도했다.
- 🔴 **이건 증거가 아니라 해석이다. 틀렸으면 버려라.**
  이 가설을 검증하는 데 시간을 다 쓰지 마라 — 통째로 무의미할 수 있다.
  **원본이 다른 곳을 가리키면 그쪽으로 가라.** 그게 내가 원하는 다른 시선이다.

## 실패 이력 — 무엇이 죽었고 무엇이 살아 있나
| 분류 | 내용 | 그 원본을 다시 봐도 되나 |
|---|---|---|
| ① 가설이 반증됨 | <...> → <반증 근거> | — 가설만 폐기. **반복 금지** |
| ② 데이터는 유효한데 분석법이 실패 | <...> → <어떻게 실패했나> | ✅ **데이터는 살아 있다. 다른 방법으로 다시 분석해라** |
| ③ 자료·계측이 부족해 결론 못 냄 | <...> | ✅ 더 정확한 접근이 있으면 재시도해라 |

🔴 **"이건 해봤는데 안 됐다"는 그 방법을 버리라는 뜻이지 그 데이터를 버리라는 뜻이 아니다.**
②·③ 의 원본은 위 `지금 바로 열 수 있는 원본` 표에 **그대로 다시 올려 뒀다** — 다른 각도로 열어라.

## 완료 게이트 — 무엇이 설명돼야 "풀렸다"고 할 수 있나
이 건은 아래가 전부 설명될 때 끝난다. 하나라도 비면 내가 되묻는다.
- G1 증상의 **인과 경로** (상관이 아니라 "A→B→C" 가 코드/로그로 이어지는가)
- G2 **조건 특이성** — 왜 이 조건에서만 나는가 (또는 왜 지금까지는 안 났는가)
- G3 **과거 실패의 설명** — 이미 실패한 시도들이 왜 안 먹혔는지 같은 원인으로 설명되는가
- G4 **반증 가능한 예측**이 하나 이상 있고 확인 방법이 있는가
- G5 수정안이 그 인과의 **어느 고리를 끊는지** 명시됐는가
- G6 남은 불확실성이 **열거**됐는가 (0일 필요는 없다. 열거만 되면 된다)

🔴 **특히 아래 증상은 반드시 설명돼야 한다** (이 건 고유):
- <증상 A> · <증상 B>

G3 가 핵심 판별식이다 — 원인 가설이 맞으면 **과거의 실패도 설명해야 한다.**

## 되물을 수 있다 — 이건 단발이 아니다
네 답변을 내가 검토한 뒤, **내 해석이 맞는지 다시 물을 수 있다.**
그러니 이번 답에서 확신이 없는 부분을 감추지 마라 — 다음 턴에 좁히면 된다.

## 요청 — 조사를 부탁한다
1. **원본부터 직접 열어봐.** 위 경로의 자료를 네 방법으로 다시 읽어라.
2. 원본에서 실제로 확인한 것과, 그것으로 무엇이 설명되는지.
3. **현재 계측이 이 증상을 포착하고 있나?** 사각지대가 있으면 그것부터.
4. 네가 보는 근본 원인. 그리고 내 가설과 어디서 갈라지는지.
5. 이 버전 기준 수정 방법을 before/after 코드로. (적용은 내가 한다)
6. 대안이 여럿이면 장단점 비교 + 이 케이스 추천. 관련 함정·주의점.
7. **확신도** — 추측과 확인을 구분해서.
   ⚠️ **"확신이 없다"는 조사를 멈출 이유가 아니다.** 확신을 올릴 읽기 전용 검증이
   남아 있으면 그걸 먼저 해라.

## 답변 형식 — Claude 가 읽고 바로 적용 판단한다
아래 순서로 써라. **1·2 를 건너뛰고 3부터 쓰지 마라** — 조사 없는 추론은 이 요청의 목적이 아니다.

1. `내가 직접 연 원본` — 어떤 파일·테이블을 **어떤 명령으로** 열었고 무엇이 나왔나.
   🔴 **비워두지 마라.** 목록만 본 것(`ls`·`find`)은 여기 쓸 수 없다.
   (`.scratch/` 에 남긴 스크립트 경로를 적어 주면 내가 재현할 수 있어 더 좋다)
2. `사용자 관측 증상에 대한 설명` — 위 관측의 **각 항목이** 설명되나.
   설명 안 되는 항목은 **그렇다고 적어라.** 얼버무리지 마라 — 그게 정보다.
3. `네가 보는 근본 원인` — 원본 증거를 근거로.
4. `내 가설에 대한 판정` — 동의 / 부분 동의 / 기각 + 이유. **짧게.**
5. `수정 방법 (before → after)` · `대안 비교와 추천` · `함정·주의점`
6. `완료 게이트 자기판정` — G1~G6 각각 **충족 / 미충족 + 한 줄 근거**
7. `확신도와 남은 불확실성` — 원인이 미확정이면 **무엇이 미확정인지** 정확히 갈라 적어라.
8. `이 머신에서 접근 불가한 자료` — 없으면 "없음".
   🔴 위 `지금 바로 열 수 있는 원본` 에 적힌 항목은 **여기 쓸 수 없다.**
   여기에 쓰려면 접근을 먼저 시도하고 **실패한 명령과 에러 메시지를 그대로** 함께 적어라.

**`send.sh` 가 frontmatter 에 세 필드를 추가한다 (2026-08-25) — 손으로 고치지 마라.**
- `thread_id` — Codex 세션. **대화의 생명줄이다.** 비면 되묻기가 끊긴다
- `origin` — 시작한 머신. docs/ 는 git 으로 5대를 오가지만 Codex 세션은 안 따라간다
- `turns` — 쌓인 턴 수. 다음 반박서의 `turn` 검증 기준이다

multi-turn 이면 문서가 이렇게 쌓인다:

```
## Codex 원문              ← 1턴 (Codex 작성)
## Claude 검토             ← Claude 가 덧붙임 · **다음 턴의 입력이 된다**
## 🔁 2턴 — Claude 반박    ← send.sh 가 반박서 본문을 박는다
## 🔷 2턴 — Codex 재답변   ← send.sh 가 -o 회수분을 박는다
## Claude 검토 (2턴) …
```

🔴 "Codex 원문을 고치지 마라, 검토는 아래 새 섹션으로" 규칙은 **그대로다.**
바뀐 것은 그 검토를 **Codex 가 읽는다**는 점뿐이다.

- Codex가 직접 쓴 파일이면 `author: codex`, `send.sh` 가 최종 메시지를 회수해 저장했으면 `author: codex-via-stdout`.
- `codex-via-stdout` 이면 **Codex 가 파일을 못 쓴 것이다.** 왜 못 썼는지 `.log/<스탬프>_stderr.log` 를 확인해라 — 응답 내용 자체가 "읽지 못했다"류의 실패 보고일 수 있다. 그 경우 분석이 아예 없는 것이니 검토할 것도 없다. **내용을 확인하지 않고 "응답 도착"만으로 성공 판정하지 마라.**
- **Codex 원문을 고치지 마라.** 검토는 반드시 아래에 새 섹션으로 덧붙인다. 섞으면 나중에 "Codex가 실제로 뭐라 했는지"를 잃는다.

## 품질 규칙

- **원본 절대경로 명시 필수** — "줄 수 있는 것"이 아니라 "지금 열 수 있는 것"으로 쓴다.
  이게 빠지면 Codex 는 목록만 보고 "자료를 더 달라"로 끝낸다 (2026-08-25 실패 사례).
- **사용자 관측·Claude 가설의 분리 필수** — 같은 섹션에 섞으면 Codex 가 관측을 가설의 근거로 읽는다.
  관측은 **인용문 블록**으로 앞에, 가설은 뒤쪽에 짧게.
- **Claude의 가설 명시 필수** — 이게 빠지면 Codex 가 내가 걸어간 길을 되밟는다.
  단 **앞에 두지 마라** — 앞에 있으면 내 시선 안에 갇힌다.
- **시도-실패 이력은 3분류 필수** — 분류 없이 적으면 "분석법 실패"가 "데이터 폐기"로 오독된다.
  ②③ 의 원본은 `지금 바로 열 수 있는 원본` 표에 **다시 올려** 행동 대상으로 남긴다.
- **실제 코드 인용 + 원본 경로 병기 필수** — 인용만 보고 판단하지 않게, 어디를 열면 원본이 있는지 적는다.
- **`response_path` 를 frontmatter에 박기 필수** — Codex에게 이름을 짓게 하면 짝이 깨지고, `send.sh` 가 이 값 없이는 동작하지 못한다.
- **쓰기 실패 폴백 문구 필수** — Codex가 저장에 실패해도 최종 메시지로 회수되도록. 이게 없으면 분석이 통째로 날아간다.
- **`run_in_background: true` 필수** — 동기로 부르면 Bash 타임아웃(최대 10분)에 걸리고, 대기 중 사용자가 다른 작업을 지시할 수 없다.
- **응답 "도착"과 응답 "성공"을 구분하라** — 파일이 생긴 것만으로 성공이 아니다. Codex가 요청서를 못 읽었다는 실패 보고가 담겨 있을 수 있다. 반드시 내용을 읽고 판정한다.
- **Codex의 무단 변경 보고는 검토보다 우선** — `send.sh` 가 🔴 로 보고하면 그것을 먼저 사용자에게 알린다. 임의로 되돌리지 않는다.
- **환경 구체적으로** — 버전·기기·툴이 원인인 경우가 많다(예: Compose Dialog 인셋, Android regex 플래그).
- **스탬프는 실측** — `date` 실행 결과만 쓴다.
- **Codex 의 작업대는 `.scratch/` 다** — 프로덕션 파일 수정만 막고 탐색·계산·네트워크는 푼다
  (2026-08-25). 예전 규칙은 "쓰는 파일은 response 하나뿐 — **샌드박스 마찰을 최소면적으로 줄인다**"
  였는데, 마찰을 줄이려다 **조사 능력을 같이 줄였다.** 그게 CONSULT 3회 실패로 확인됐다.

## 보안

- **PAT·API 키·토큰·비밀번호·개인 메모 본문**은 절대 넣지 않는다.
- 파일 경로·함수명·버전은 넣어도 된다. 비밀값이 코드에 있으면 `<REDACTED>` 로 마스킹.
- request 파일은 외부(Codex)로 나가고 **git에도 커밋된다** — 유출되면 안 되는 값은 원천 배제.

## 출력 형식

`send.sh` 를 던진 뒤 채팅에는 **짧게** 이것만 낸다. 사용자가 할 일이 없으므로 지시할 것도 없다.

1. **모드 한 줄** — 어느 모드로 갔는지. 맥락으로 판정했으므로 **반드시 밝힌다.**
   - `모드: 검토(Codex는 분석만)` / `모드: 코드리뷰(git diff, Codex는 분석만)` / `모드: 수정(Codex가 직접 고침)`
2. **무엇을 대상으로 했는지 한 줄**
   - CONSULT·EDIT → 어느 문제로 썼는지 (자동 특정했다면 반드시)
   - REVIEW → 리뷰 범위 (`커밋 안 된 변경` / `main 대비` / `커밋 abc123`)
3. 생성한 파일 경로 (요청서 또는 리뷰 결과가 생길 경로)
4. 한 줄: `Codex 에 넘겼습니다. 끝나면 제가 자동으로 받아 검토합니다 — 그동안 다른 작업 지시하셔도 됩니다.`

요청서 본문 전체를 채팅에 다시 뿌리지 않는다 — 파일이 정본이다.
검토가 끝난 뒤에는 채택/보류/기각과 적용 계획을 보고한다.

🔴 **모드를 밝히는 게 중요하다.** 키워드가 아니라 뜻으로 판정하므로 오판 가능성이 있다.
사용자가 한 줄만 보고 "그게 아니라 이거야" 라고 바로잡을 수 있어야 한다.

- **Codex 가 남긴 자식 프로세스의 지연 변경** — `codex exec` 가 반환한 뒤 백그라운드 자식이
  파일을 바꾸면 사후 1회 스캔에는 안 잡힌다
- **디렉토리·메타데이터** — 빈 디렉토리 생성, 권한/ACL, NTFS ADS, symlink/junction
- **줄바꿈이 포함된 파일명** — 줄 단위 처리라 한 파일이 여러 경로로 쪼개진다
- **원인 귀속 불가** — OneDrive 동기화나 다른 프로세스의 변경과 Codex 의 변경을 구별할 수 없다.
  변경이 잡히면 `.log/<스탬프>_events.jsonl` 에서 Codex 가 실제로 실행한 동작을 대조해라

위협 모델은 **"프롬프트를 안 지킨 Codex"** 다. mtime 을 일부러 되돌리는 능동적 은폐는 상정하지 않는다.
그 수준까지 막아야 하면 `CR_SANDBOX=read-only` 를 쓰는 것이 근본적이다 — Codex 에게 쓰기 권한을
아예 주지 않고, `-o` 로 받은 최종 메시지를 이 스크립트가 응답 파일로 저장한다. **코드 변경 없이
환경변수만으로 전환된다** (실측 검증됨).

## 인자 — 한글로 말하는 게 정상 사용법이다

사용자는 STT 로 말한다. 영문 플래그를 요구하지 마라. **뜻으로 알아듣는다.**

| 이렇게 말한다 | 간다 |
|---|---|
| `/codex_rescue` (인자 없음) | ★ **가장 흔함.** CONSULT. 막힌 걸 Claude 가 맥락에서 직접 특정 |
| `검토요청해` · `분석해줘` · `봐달라고 해` · `물어봐` | CONSULT |
| `리뷰시켜` · `리뷰해줘` · `바뀐 거 검토해` · `커밋 전에 훑어줘` | REVIEW |
| `리뷰시켜 인증 위주로` · `main 기준으로 리뷰해` | REVIEW + 집중지시/스코프 |
| `검토및 수정요청해` · `분석하고 수정시켜` · `수정시켜` · `고쳐줘` | EDIT (**확인 한 줄 받고** 진행) |
| `코덱스와 대화해` · `핑퐁으로 물어봐` · `짧게 주고받아봐` | **CHAT** — 명시할 때만 |
| `<request 파일 경로>` (인자 전체가 경로) | RESUME |
| `다시 물어봐` · `되물어` · `그거 반박해봐` · `왜 그렇게 봤는지 물어봐` | **FOLLOWUP** (직전 CONSULT 를 이어서) |
| `help` · `사용법` · `?` | HELP |
| 문제 텍스트 (`로그인이 안 돼`) | CONSULT + 그 문제에 집중 |

영문 플래그도 계속 받는다(`--readonly` · `--edit` · `--review`) — 하위 호환이지만 권장하지 않는다.

**서술형은 모드 지시가 아니다.** "리뷰가 안 돼" · "수정이 안 먹혀" 는 **문제 텍스트**다 → CONSULT.

## 파일

```
~/.claude/skills/codex_rescue/
  SKILL.md    이 문서
  send.sh     codex 호출 + 응답 회수 + 변경 실측. Claude 가 백그라운드로 던진다
```

`send.sh` 진입점은 세 개다.

```bash
# CONSULT / EDIT — 요청서 기반 (mode 는 frontmatter 가 정한다). 1턴
send.sh <request 파일 경로>

# FOLLOWUP — CONSULT 2턴 이후. 반박서 기반. **백그라운드**(CHAT 과 반대)
send.sh --followup <반박서 경로>

# REVIEW — git diff 기반. 요청서가 없다
send.sh --review --slug <슬러그> [--subject "<한 줄 제목>"] [--uncommitted|--base <브랜치>|--commit <SHA>] [집중지시]

# CHAT — 핑퐁. 요청서가 없고 **동기로** 부른다 (백그라운드 금지)
send.sh --chat --start --slug <슬러그> [--subject "<한 줄 제목>"] [--look <경로>[:<시작>-<끝>]]... [--explore] <던질 말>
send.sh --chat --resume-stamp <대화키> --slug <슬러그> [--look <경로>]... <던질 말>
send.sh --chat --close-stamp  <대화키> --slug <슬러그>                        # 닫기만 (codex 안 부름)
```

CHAT 은 스크립트 맨 앞에서 갈라져 **나머지 배관을 전혀 타지 않는다** — 락(세션별로 따로 건다)·
marker·baseline·변경 감지·`status.json`·heartbeat 없이 조기 종료한다. 그래서 기존 세 모드에
회귀를 만들지 않고, `.log/` 에 이벤트를 안 남기므로 진행 패널에도 뜨지 않는다.

환경변수는 양쪽 공통이다 — `CR_MODEL` · `CR_SANDBOX`(REVIEW·FOLLOWUP 은 read-only 고정이라 무시) ·
`CR_WIN_SANDBOX` · `CR_ALLOW_EDIT` · `CR_DRYRUN` · `CR_NETWORK`(기본 허용, `false` 로 차단) ·
`CR_CONSULT_MAX_TURN`(되묻기 턴 상한, 기본 **11**).
`CR_CHAT_LIMIT`(초, 기본 **60**) 과 `CR_CHAT_LOOK_MAX`(바이트, 기본 65536) 은 **CHAT 전용**이다.
⛔ `CR_TIMEOUT` 은 제거됐다 — Windows 에서 작동하지 않아서다(실측). 쓰면 스크립트가 거부한다.
CHAT 의 상한이 되살아난 것은 `timeout` 명령을 쓰지 않고 백그라운드 + 1초 폴링으로 직접 죽이기
때문이다(TERM → 2초 → KILL). Windows 에서 실제로 프로세스가 사라지는 것을 실측했다.

`send.sh` 를 고쳤으면 다른 머신에도 배포해야 한다 — `/skill_cp_install push codex_rescue`.
