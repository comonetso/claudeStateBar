# browser-check — 실제 브라우저에서 Claude 가 웹 페이지를 직접 보고·누르고·진단한다

서버 로그와 소스만 보고 "시험 통과"라 하지 않는다. Claude Code 가 **ego lite**(사용자 Windows PC 에 둔, 에이전트용 Chromium 브라우저)에서 페이지를 열고, 눌러 보고, 화면·콘솔·네트워크·CSS·반응형·접근성·성능을 직접 확인한다. PC 에서도, PC 의 작은 중계 프로그램을 거쳐 서버에서도(ssh) 같은 플러그인이 돈다.

- 발동: 한국어 자연어 — "화면 확인해 봐", "CSS 깨졌는지 봐", "콘솔 에러 봐", "API 실패 봐", "반응형 봐", "다크모드 확인", "접근성 점검", "성능 봐", "이 버튼 눌러 봐", "실시간 동기화 확인", "로그인 풀렸어", "전체 흐름 시험해" (STT 받아쓰기 변형 포함)
- 호출명: `browser-check:browser_check`

0.1.x 까지는 다른 브라우저(Aside)를 다뤘고, 0.2.0 부터는 ego lite 만 쓴다. 사용자가 평소 쓰는 브라우저의 탭에는 닿지 않는다.

## 점검이 도는 방식
플러그인은 PC 와 서버 어디서나 Bash 도구의 경로에 명령 하나, `browser-check` 를 올려 둔다. 흔한 점검은 대본이 필요 없다.

```
browser-check look https://example.com/
browser-check look https://example.com/search --fill "#q" "hello" --click "text=Search" --wait ".results"
browser-check look https://example.com/ --width 390 --dark --full
```

`look` 은 페이지를 열고, 준 순서대로 단계를 하고(누르기·입력·고르기·키 누르기·기다리기), 다음에 누를 곳 번호가 붙은 화면 글·캡처·콘솔과 네트워크 문제·페이지가 보낸 GET 이 아닌 요청을 모두 돌려준다. 그래서 무언가를 저장하거나 보낸 누르기는 결과에 드러난다. 단계가 실패하면 상태가 `step-failed`, 종료 코드가 1 이 되고 이유를 결과에 적는다. 단계가 연 창은 그 창의 글·캡처·문제·보낸 요청과 함께 보고한다. `look` 은 매번 페이지를 새로 열기 때문에 앞선 결과의 번호(`@12`)를 거절하고 그 옆에 찍힌 `loc=` 를 쓰라고 알려 준다. `browser-check api click` 은 함수가 무엇을 받는지 ego 자체 도움말로 답한다. 그 밖의 일은 짧은 대본으로 한다 — `browser-check run <대본.mjs>`, 또는 대본을 표준 입력으로 주는 `run -`.

대본은(`look` 이 만드는 대본도) ego-browser 자체의 Node 런타임 안에서, 자기 몫의 작업 공간(task space — 사용자 탭과 키보드 초점을 건드리지 않는 에이전트용 탭 묶음)에서 돈다. 플러그인은 대본 앞에 도우미(`bc.*`)를 붙인다 — 공간을 열고 반드시 다시 닫기, 닫기 전에 진행 중인 요청이 0 이 되기를 기다리기, 캡처, 콘솔·네트워크 문제 모으기, 보낸 요청 목록, 쓰기 차단, 페이지 안 점검 도구 돌리기. 그림은 파일로, 데이터는 JSON 으로 돌아온다. 아직 설정이 안 된 기기면 답에 그렇다고 하고 무엇을 돌릴지 알려 주므로, 따로 점검 단계를 먼저 밟지 않는다. 읽기 요청만 열어 두는 페이지(긴 요청을 열어 두는 실시간 페이지는 늘 하나를 열어 둔다)는 기다린 뒤 빈 페이지로 옮겨 닫는다. 쓰기 요청이 아직 진행 중인 페이지는 닫지 않고 `leftOpen` 으로 알린다.

PC 에서는 대본이 `ego-browser` 로 바로 간다. 서버는 그렇게 못 한다 — ego lite 는 네트워크 포트를 열지 않고 관리자 권한으로 부르는 쪽을 거부한다("ego-browser is running as administrator"). 그런데 Windows 에서 관리자 계정의 ssh 접속은 늘 관리자 권한이다. 그래서 `relay install` 이 PC 에 중계 프로그램을 둔다. 이 프로그램은 사용자의 일반 권한 로그온 세션에서 돌고, 127.0.0.1 로만 받으며, 암호는 자기 폴더에 둔다. 서버는 ssh 로 중계의 진입 파일에 대본을 넘기고, 진입 파일이 중계에 건넨다. 결과도 같은 길로 돌아온다. ssh 연결은 2분 동안 다시 쓴다. 실행이 세 번 잇따라 시간 초과로 끝나면 중계가 ego 를 시험해 보고, 그것도 실패할 때만 ego 를 다시 켠다 — 먼저 정중히 닫고, 그래도 남을 때만 강제로 끄며, 프로필과 로그인은 그대로 두고, 15분에 한 번까지만.

## 캡처
ego 는 창이 최소화돼 있으면 보통 캡처를 거부하고, X 로 닫은 창은 실제로는 숨긴 것이라 그리지 않는다. `bc.shot` 은 세 경우를 다 다룬다. 먼저 보통 캡처를 해 보고, 거부되면 화면 연속 전송(screencast — 최소화 중에도 계속 그린다. 첫 그림은 마지막 변화 전 화면일 수 있어서 받은 그림마다 답을 보내고 잠깐 기다린 뒤 마지막 그림을 쓴다)으로 받는다. 그림이 한 장도 안 오면 ego 창이 전부 X 로 닫힌 것이라 ego 를 다시 불러 숨은 창을 띄우고 곧바로 최소화한 뒤(실측 화면 노출 65~185ms) 캡처한다. 그래서 사용자는 ego 를 최소화해 두든 닫아 두든 상관없다. 페이지 전체 캡처도 최소화 상태에서 된다. 한 장을 찍는 동안 화면 크기를 페이지 높이만큼 늘렸다가(CSS 10000 픽셀까지, 모바일 폭은 5000 까지) 되돌리고, 어디까지 찍었는지 결과에 적는다. 페이지 안의 칸만 스크롤되는 화면은 늘어나지 않으므로 그 경우에는 여전히 나눠 찍어 이어 붙인다. 한 번도 보인 적 없는 최소화 창에서 연 탭은 페이지 크기가 0×0 이라 아무것도 그리지 않는다. `look`·`bc.run`·`bc.shot` 은 창은 건드리지 않고 그런 페이지에 창 크기를 준다.

## 콘솔 오류
ego 는 콘솔 메시지와 호출 스택을 자동화 통로에서 숨긴다. 페이지가 이를 보고 자동화를 알아챌 수 있어서다. SDK v2.2(ego lite 0.6.2)부터는 이 숨김이 기본으로 켜져 있어, 오류를 내는 페이지도 오류가 없는 것처럼 보인다. 오류를 못 보는 점검 도구는 깨끗한 페이지라고 잘못 보고하게 되므로, `bc.watch` 는 숨김을 끈다. 끄는 동안에는 페이지가 통로를 알아챌 수 있다. 그런 다음 시험 글 한 줄을 써서 실제로 들어오는지 확인한다. 결과는 `problems.consoleState` 에 있다. `on` 이면 개수를 믿을 수 있고, `hidden`(`--no-console`, 자동화에 반응하는 사이트용)과 `blind` 면 콘솔·예외 개수를 모른다는 뜻이라 0 이 아니라 `null` 로 나온다.

## 시간 제한
모든 대본은 ego 안의 오래 사는 Node 프로세스 하나에서 돈다. 그래서 부른 쪽을 끊어도 대본은 멈추지 않는다. 실측에서 계속 돌았고 공간도 열린 채였다. 그래서 대본이 브라우저를 부를 때마다 자기 제한 시간(`--timeout`, 기본 300초)을 확인해, 부른 쪽이 포기하기 조금 전에 스스로 멈추고 공간을 닫는다.

## 쓰기 차단
`--guard-writes [--allow-write <경로>]…`, 또는 사이트 규칙 `guardWrites: true` 와 `writeAllow`. 페이지 안에서 GET·HEAD·OPTIONS 가 아닌 fetch·XMLHttpRequest·sendBeacon·폼 제출을 허용 경로가 아니면 막고, 막은 목록을 결과에 싣는다. 켜자마자 없는 경로로 POST 를 보내 막히는지 스스로 시험한다. 웹소켓 메시지, 서비스 워커가 스스로 보내는 요청, submit 이벤트 없는 최상위 POST 이동은 막지 못한다. 로그인 사이트에서는 토큰 갱신 경로를 허용해야 한다 — 차단을 켜자 사이트의 갱신 POST 가 막혀 페이지가 로그인 화면으로 떨어졌다(서버에는 아무것도 가지 않아 로그인 자체는 살아 있었다). 차단이 로그인·세션 갱신처럼 보이는 경로의 요청을 막으면 결과의 `hints` 가 그 요청과, 그 경로만 통과시키는 `--allow-write` 를 알려 준다. 차단을 끈 채 쓰기 요청이 나간 경우와, 허용한 경로가 통했는데 사이트 규칙에는 아직 없는 경우도 알려 준다. 페이지가 다른 문서로 넘어가기 전(로그인 화면으로 이동)에 막은 요청도 목록에 남는다. Windows 의 Git Bash 가 Git 폴더 아래 경로로 바꿔 넘긴 값(`C:/Program Files/Git/api/…`)은 원래 경로로 되돌려 쓴다. 예전 차단이 쓰던 브라우저 단계 가로채기는 ego 에서 멈춤이 생겨 거부한다. 누르기로 열린 창에도 알아차리는 즉시 차단을 걸고, 공간은 그 창의 요청까지 끝난 뒤에 닫는다. 창이 뜨는 첫 순간에 보낸 POST 는 그보다 먼저 나간다(실측에서 서버에 도착했다). 이 방식으로는 막을 수 없어서 결과의 `popups[].beforeGuard` 와 `hints` 에 그 요청을 적는다.

## 시험한 환경
Windows 11 에서만 시험했다. ego lite 가 깔린 PC 와, ssh 로 그 PC 에 닿는 Linux 서버 세 대다. macOS 에서는 시험하지 않았고 어떻게 동작할지 모른다. 두 부분은 처음부터 Windows 전용이다. 서버가 PC 의 ego 를 쓰게 하는 중계(작업 스케줄러·`%LOCALAPPDATA%`)와, ego 창이 모두 X 로 닫혔을 때 다시 띄우는 부분(`window.ps1`)이다.

## 설치
1. Windows PC 에 ego lite 를 설치하고(https://lite.ego.app/) 첫 설정을 마친 뒤, Claude 가 점검할 사이트에 ego 에서 로그인해 둔다. ego 는 Chrome·Edge 에서만 가져오기가 된다.
2. PC 와 각 서버에서 `claude plugin install browser-check@comonetso`.
3. PC 에서 `browser-check relay install` — 중계를 `%LOCALAPPDATA%\browser-check\relay` 에 복사하고 작업 스케줄러 항목 "browser-check ego relay"를 만든다(로그온 때와 1분마다, 이미 떠 있으면 바로 끝남, 시간 제한 없음, 일반 권한). `relay status`·`relay uninstall` 로 확인·제거한다.
4. 각 서버에는 PC 로 키 로그인되는 ssh Host 가 있어야 한다. 처음 쓸 때 `setup` 이 `~/.ssh/config` 의 Host 마다 중계가 있는 PC 인지 물어본다. 하나가 답하면 설정을 쓰고, 여럿이면 어느 것인지 묻고, 없으면 무엇이 빠졌는지 알려 준다.
5. **비공개 실행 설정**은 `${CLAUDE_PLUGIN_DATA}/config.json`(권한 0600, 상위 폴더 0700 — Windows 에는 이런 권한 비트가 없어 그쪽은 검사하지 않는다). Claude Code 는 Bash 도구에 `CLAUDE_PLUGIN_DATA` 를 넘기지 않으므로, 명령이 플러그인이 설치된 위치에서 이 폴더(`<plugins>/data/browser-check-comonetso`)를 알아낸다. `BROWSER_CHECK_CONFIG` 를 주면 그쪽을 쓴다. 처음 쓸 때 `setup` 이 만들고, 넣은 값을 보여 주며, 지금 판 설정은 덮어쓰지 않는다. Aside 판 설정은 알려 주고, `setup --migrate` 가 사이트 규칙을 남긴 채 다시 쓴다(옛 파일은 백업). 사이트 규칙은 빈 채로 시작하며, 그것이 안전한 기본값이다. `config/example.json`·`config/schema.json` 참고.
6. `browser-check doctor` 가 상태를 보여 준다 — PC 에서는 ego-browser·판 번호·창 상태·중계, 서버에서는 중계의 답. Claude Code 밖(cron·맨 ssh)에서는 `node <플러그인 폴더>/scripts/browser-check.mjs` 나 `<플러그인 폴더>/bin/browser-check` 로 부른다.

## 안전 (전문: `skills/browser_check/SKILL.md` §1)
`look` 단계와 대본의 누르기·입력은 실제 사이트의 버튼을 누르므로, 저장·보내기·삭제가 되는 것은 사용자 승인을 먼저 받고, 보낸 것은 결과에 목록으로 나온다 · 자기 작업 공간만 · ego 창을 Claude 가 옮기거나 크기를 바꾸거나 최소화하지 않는다(캡처 때 닫힌 창을 최소화로 다시 띄우는 것 하나만 예외) · 로그인 사이트에서는 진행 중 요청이 0 이 된 뒤에만 공간을 닫고, 아니면 열어 둔 채 보고한다 · 데이터 변경은 그 대상에 대한 명시적 승인이 있을 때만 · 클립보드·다운로드·OS 선택 창·브라우저 단축키 금지 · 쿠키·저장소 명령, 브라우저 닫기, 창 크기, 요청 가로채기, 대상 만들기는 거부 · 비밀값은 읽지도 남기지도 않는다(중앙 가리기) · 로그인·2단계 인증·CAPTCHA 는 사용자에게 넘긴다 · 쓰기 차단에는 빈틈이 있다. 누르기로 뜬 새 창이 뜨는 첫 순간에 보내는 POST 는 차단이 닿기 전에 나가고, 결과가 그런 요청을 알려 준다(`popups[].beforeGuard`).
